## 1. 目的

AI が「使いたい Provider の URL」を Router に渡し、
**設定に事前登録されていない宛先に対しても購入を成立させる。**

## 3. スコープ

### 3.1 本スライスで満たすこと

- **送信側（outbound）の宛先を動的にする**
- 任意 URL を安全に fetch する（SSRF 防御）
- 受取先の扱いを**明示的に選んだ方式**で認可する
- 宛先が動的になったことを**承認の対象に反映**する

### 3.2 本スライスで満たさないこと（理由付き）

| 対象 | 理由 |
|---|---|
| **受信側（inbound）の動的化** | 前提 9 の非対称性。owner の構想は「使いたい Provider を選ぶ」= 送信側。受信を動的にすると前提 8 の blocker が全面化する |
| レート取得・FX・異資産変換 | 前提 3・4。**現時点で解くべき問題が存在しない**。seam だけ空ける |
| 手数料の価格設定 | 上と同じ理由。`fee` を足す場所だけ用意する |
| Provider の選定・比較 | Router の役割ではない（AI かディレクトリの仕事） |
| Lightning レール | `lightning-feasibility.md` §6.2 で「参照実装が出るまで待つ」と判断 |

## 4. 受取先の認可方式: **TOFU（初回のみ承認）**

### 4.1 なぜこれを選ぶか

調査が示した判断基準:

> **運用者が、その Provider の正しい `payTo` を事前に・帯域外で知っているか。**

AI が任意の Provider を指名するなら **知らない**。したがって:

- **(a) オリジン allowlist に委譲**は不可。**designation を利害当事者に委ねる**ことになり、
  confused deputy が構造的に成立する（Miller/Yee/Shapiro の Property A 違反）。
  加えて **`dynamicPayTo` は x402 の正式機能**なので、1 オリジンが
  パスごとに別の受取先を返すのは想定された挙動である
- **(b) 毎回承認**は安全だが、owner の要件（AI が自由に使う）と衝突する
- **(c) TOFU** は **EU 2018/389 Art. 13 に法的前例がある**
  （信頼済み受取人リスト: 作成・変更時に SCA 必須、以降は**金額上限なしで免除**）

### 4.2 要件

- **FR-1 初回は承認**: 未知の `(resource, network, asset) → payTo` の組は、
  **人間の承認を要する**。承認対象には **オリジン・リソースパス・`payTo`・金額**を含める
- **FR-2 以降は自動**: 承認済みの組は、予算の範囲内で**承認なしに購入できる**
- **FR-3 AI は信頼ストアを変更できない**: Art. 13 の「creates **or amends**」が境界。
  **追加・変更・削除はすべて人間の操作**とする。
  **MCP ツールから信頼エントリを操作する経路を作らない**
- **FR-4 束縛の粒度は `(resource, network, asset)`**:
  1 ホストが複数の `payTo` を正当に持つ（実測で約 42% が 2〜3 個）ため、
  **ホスト単位では命題が定義できない**
- **FR-5 ドリフトで停止**: 承認済みの組で `payTo` が変化したら、
  **自動では払わず再承認を求める**（x402-list の `payto_changed` が 30 日で 40 件を記録）
- **FR-6 失効を設計する**: **前例が存在しない**ため自前で定める。
  最低限、エントリに「最終利用時刻」と「有効期限」を持たせ、期限切れは再承認とする

### 4.3 MPP レールの特例

**FR-7**: `fundsMoveOnCredential` が true のレールでは、
**初回承認を credential 生成より前**に行う。資金が `sign` で不可逆に動くため
（`fundsmove-requirements.md` で確定した性質）。

## 5. SSRF（必須要件）

**FR-8**: 認可は**あらゆるネットワーク要求の前**に行う。
URL パース後**かつ DNS 解決後**に禁止宛先を拒否し、**接続時に強制**する。

対象: IPv4/IPv6、IPv4-mapped、10進/8進/16進表記、loopback・private・link-local、
内部 DNS 名、メタデータ endpoint（`169.254.169.254` 等）。

- **ホスト名の allowlist だけでは不十分**（許可ホストが内部アドレスに解決し得る）
- リダイレクトは**無効のまま維持**（`redirect: "error"` は既に両 adapter にある）
- タイムアウトは時間を制限するだけで、**アクセスを認可しない**

## 6. 束縛と記述子

**FR-9 不変 purchase descriptor**: 動的購入には、
**検証済み fetch URL・method・両レール・承認条件**を含む**不変記述子**を設け、
**サーバ生成の不透明な識別子**を割り当てる。
credential はその識別子に束縛し、**常に保存された記述子を実行する**。
purchase 時の入力から**再構築しない**。

**FR-10 URL 正規化で同一性を決めない**: 正規化の攻撃面が広すぎる
（IDN、既定ポート、多重デコード、クエリ重複、userinfo、fragment）。
`userinfo` と `fragment` は**拒否**する。クエリの扱いは明示的に定義する
（現状 `allowQuery=false`）。

**FR-11 同一 `requestId` で宛先が違えば衝突させる**: 現状は `routeId` しか比較していない
（`orchestrator.ts:288-298`）。

## 7. 受信条件と予算

**FR-12 受信条件の権威を定義する**: 現状 `source.amount`/`asset`/`network` は
設定の route 由来（`orchestrator.ts:308-324`）。route 登録を外すと**誰が決めるか未定義**になる。
動的購入用の**支払いプロファイル**を設定に持つ。
前提 3・4 により、**当面は受信資産 == 送信資産**でよい。

**FR-13 予算を宛先単位にする**: バケットを `(network, asset, payTo)` に拡張する。
理由は 2 つ:
1. 悪意ある宛先 1 つが**共有予算を食い潰す**のを防ぐ
2. **未知の宛先への初回上限を小さくできる**（被害額が構造的に小さくなる）

**FR-14 動的 route に限り同一資産を強制する**（**自己検証で修正**）。

> **初稿の誤り**: 「受信資産 ≠ 送信資産なら quote を成立させない」と書いたが、
> これは**稼働実績のある経路を壊す**。
> `u01r-live` は **zETH（Sepolia）→ USDC（Base Sepolia）の異資産**で、
> 実決済を通している（`u01r-requirements.md` §26）。

**異資産そのものは危険ではない。** 既存の静的 route が安全なのは、
**運用者が受信額と送信額の両方を固定**しており（`orchestrator.ts:310` は
`route.source.amount` を使う）、**レートを参照していない**ため
Router が価格リスクを持たないからである。損得は設定時に運用者が引き受けている。

危険なのは「**動的 route で、上流価格からレート換算して受信額を決める**」場合だけ。
したがって制約は:

- **静的 route（設定済み）**: 異資産を**許す**（現状維持。既存経路を壊さない）
- **動的 route（本スライスで追加）**: **受信資産 == 送信資産でなければ quote を成立させない**

動的 route でこの制約を外すことが、
**「レート取得と価格リスクの引き受け方を決める必要がある」というトリガー**になる。

## 8. 受容するリスク（明記する）

| リスク | 理由 |
|---|---|
| **malicious payee**（承認済みの正当な宛先が無価値なデータを返す） | 受取先の固定は **redirection** を防ぐが誠実性は保証しない。UK Finance 2026 ではこの分類が記録的高水準（£437m、+35%）。escrow / 紛争処理 / レピュテーションは**本スライスの範囲外** |
| ステーブル間スリッページ（実測 60bp） | 同一資産に限る間は発生しない。異資産対応時の課題 |
| ディレクトリの記載 | **信頼しない**。参考情報としてのクロスチェックに留める（前提 6・7） |

## 12. 独立レビュー結果: **REJECT** — blocker 4 件を反映する

レビュー実施: 2026-10-01、`gpt-6-astra`、`--sandbox read-only`。
**blocker 4 件 + 設計不備 7 件。** 実ソースで再確認して要件を改訂する。

### 12.1 blocker 1: FR-14（**レビュー到着前に自分で発見・修正済み**）

§7 の FR-14 を動的 route 限定に修正した（commit `771a676`）。
レビューも同じ指摘で、追加で 2 点:

- **資産の同一性は `(network, token)` で定義する**。
  トークン文字列の比較だけでは**ネットワーク跨ぎの経済的同一性を示さない**
- `u01r-requirements.md` §26 の実績は **testnet の決済**であり、mainnet の実績ではない

### 12.2 blocker 2: 送信側限定でも起動時 map の問題は消えない

**§3.2 の scope cut は「受信条件を静的に保つ」点では妥当だが、
「既存の受信/API 実装を変えずに済む」とは言えない。** 静的前提が広範に存在する:

| 箇所 | 前提 |
|---|---|
| `main.ts:123,134` | 起動時の route / binding map で dispatch |
| `orchestrator.ts:283` | 未登録 route を上流読取**前**に拒否 |
| `app.ts:286,313` | quote と purchase が独立に設定済み route を要求 |
| `projection.ts:37` | `RouteConfig` を要求。`resource` は Router の購入 URL で、宛先 `payTo` は**無い** |
| `client/index.ts:295` | `/v1/routes/${routeId}/resource` を強制 |
| `client/types.ts:152`, `mcp/tools.ts:180` | quote は `routeId` + `requestId` のみ受け付ける |

→ **FR-15（新規）**: **「静的な受信条件」と「動的な購入束縛」を区別する**要件にする。
固定の payment profile は受信 adapter を保てるが、
**各購入は動的な宛先を credential と記述子に束縛しなければならない**。
U-4 は問題を先送りしているだけなので、**設計フェーズで範囲を確定する**。

### 12.3 blocker 3: `resource` が信頼キーとして曖昧

現状 `resource` は**公開上は Router の URL**（`projection.ts:46`）であり、
送信 adapter は別途「上流が申告した resource と fetch URL」を照合する（`x402.ts:309`）。
**公開 resource を TOFU キーに流用すると、複数の上流 URL が 1 つの信頼エントリを共有し得る。**

→ **FR-4 改訂**: 信頼キーは
**「検証済みの送信先オリジン + 正確なパス + method + 明示的なクエリ方針」**とし、
**実際に fetch した URL に紐づける**。
**異なるパスは独立した信頼を要する**（人間が明示的に広いスコープを承認した場合を除く）。
FR-10 の「正規化しない」は**同値性を定義しない**ので、別途定義が必要。

**クエリは送信経路でも既に拒否されている**（`x402.ts:266`、`mpp.ts:213`）。
**この規則を維持するか、置き換えを明示して試験する。**

### 12.4 blocker 4: 「MCP に編集ツールを作らない」では人間の権限を担保できない

**最も危険な指摘。** 既存の承認は `quoteId` との**文字列一致のみ**
（`orchestrator.ts:392`、自分で確認）であり、**人間が操作した証拠ではない**。
AI は `quoteId` を知っているので自分で渡せる。

→ **通常の MCP 購入の後に受取先を自動登録すると、
専用ツールが無くても AI が信頼を作れてしまい、AC-3 の狭い検査を通過する。**

→ **FR-3 改訂（必須）**:
- 登録・変更・削除・期限延長には、**購入とは別に認証された人間の操作**を要する
- **通常の quote / purchase は決して信頼を昇格させない**
- **そのエントリが誰の権限を表すか**を定義する（Router 運用者 / 支払 principal / 明示的共有）。
  1 つの principal の承認が**他の principal を黙って認可しない**こと

→ **FR-6 改訂**: 機械が更新する `lastUsedAt` と、
**人間が制御する認可フィールド**を区別する。
区別しないと、自動更新が FR-3 と矛盾するか、繰り返し購入が信頼を黙って延長する。

### 12.5 blocker 6: 予算キー変更に移行計画が無い

`budget_reserved` は `{network, asset, amount}` のみで **`payTo` を含まない**
（`orchestrator.ts:449`、自分で確認）。`Budget.load()` はこの行だけから再構築する（`budget.ts:61`）。
→ **キーを変えると、過去の消費が新バケットに入らない / 飛ばされる / 起動できない。**

→ **FR-13 改訂**:
- **versioned replay と保守的な移行方針**を要件にする。
  過去の受取先は対応する intent から復元できる可能性があるが、**明示的で検証された join** が必要。
  **履歴が欠落・曖昧な場合は、消費枠を復活させてはならない**
- **集約 `(network, asset)` 上限を受取先サブ上限と併存させる**。
  置き換えると**承認済み受取先の数だけ総額が増える**
- 受信レグの予約の扱いと、**unknown 終端の予約保持**を維持する

| 10 | 正しい。ただし**送信 adapter は独自にクエリを拒否**しており、fixture 検証は別経路 |

**scope cut は「変換リスクが存在しない」と主張せずに、
製品判断として正当化できる。**

### 12.8 U-1 の改訂

journal は **at-most-once だけでなく予算予約も保持している**。
汎用イベント・直列 append・fsync・プロセス全体の flock
（`journal.ts:16,120,254`）は信頼の付与/変更/撤回イベントを**支持できる**。
既存 reducer は無関係イベントを無視できる。

ただし共有 journal でも**イベントスキーマ・権限検査・再生規則**が必要で、自動的に正しくはならない。
別ストアは**別の耐久性/ロック境界**を持ち込み、
**撤回・購入認可・予約の順序**を定義する必要がある。
**独立 CLI は、既にロックされた journal に並行 append できない。**

→ **どちらを選ぶ前に、クラッシュ時と並行時の意味を明示する。**
