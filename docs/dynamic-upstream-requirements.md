# 要件: 動的上流 URL（呼び出し側が Provider を指定する）

> 2026-10-05。`generalization-requirements.md` §15〜§17 の確定版は **FR-0（AI は登録権限を持たない／
> 宛先は設定ファイル）** で終わり、動的 URL は実装しなかった。SSRF 防御 A・B の受け入れが両方通り
> （`ssrf-app-guard-design.md` §15・§16、`ssrf-egress-design.md` §27）、`ssrf-requirements.md` §9 の
> release gate が満たされたので、**FR-0 を外す場合の要件**を本書で定める。
> 旧 2 文書は経緯として残し、**動的 URL については本書が上書きする**。
> A・B の受け入れは**内部へ届かないこと**を示すだけで、本機能の乱用耐性は示していない。

## 1. owner の決定（2026-10-05）

| # | 決定 | 意味 |
|---|---|---|
| D-1 | **受取先は呼び出し側が購入ごとに承認する** | 運用者は宛先を保証しない。信頼ストア・登録・TOFU は作らない |
| D-2 | **受信額 = 上流の提示額 + 手数料**。対象は**運用者が設定で指定した資産ペアに限る** | レート取得は持ち込まない。手数料は取る |
| D-3 | **本番の `/mcp` から匿名で誰でも使える**。rate limit を掛ける | 乱用・SSRF は多層で防ぐ（A・B は済み） |

## 2. 前提の転換

旧要件は「**運用者が** `payTo` を保証できるか」を問い、信頼ストアが必要になり、
「購入する AI が自分で登録できてしまう」（旧 §12.4・§14）で行き詰まった。

本番の構成では**受信レグは呼び出し側が自分の鍵で払い、送信レグは運用者のウォレットが払う**
（`tools/remote-mcp.ts:6-11`）。したがって:

- 「**どこに払うか**」は呼び出し側が自分の資金について決める。Provider に直接払う場合と同じ責任分担である
- 「承認が人間のものか」は**呼び出し側のエージェント環境の責任**であり（現行の静的 route も同じ）、
  Router の責任は**承認に必要な事実を偽りなく示し、示したものだけを実行する**こと

これにより旧 FR-0・信頼ストア・ドリフト検知・`payTo` サブ予算は不要になる。

**ただし `payTo` の認可が呼び出し側に移っても、次は運用者の問題として残る**（1 回目レビュー指摘 1・3）:

| 運用者が守るもの | 理由 |
|---|---|
| **署名権限** | 送信の署名・broadcast は運用者の鍵で行う。上流が作った offer に署名する以上、**何に署名してよいか**は運用者が決める |
| **流動性と費用** | 送信元本は受信で回収できても、**送信手数料・失敗した送信・受信資産と送信資産の偏り**は運用者が負う |
| **内部と自分の依存先** | 内部ネットワーク（A・B）に加え、Router 自身の公開口・facilitator・RPC |
| **サービスの継続** | 匿名の相手が**払わずに**止められないこと |

## 4. スコープ

**満たすこと**: 呼び出し側が上流 URL を渡して quote を取り、承認し、払い、応答を受け取る。
**動的になるのは送信先だけ**。受信の口座・レール・価格方針は運用者の設定が権威のまま。
ただし受信の**額と credential の束縛は quote ごとに変わる**ので、受信側の実装は変更対象に含む。

**満たさないこと**

| 対象 | 理由 |
|---|---|
| 受信の口座・レールの動的化、新しいレール | 送信先の話で足りる |
| レート取得・運用者が指定していない資産ペア | D-2 |
| GET 以外の method、要求本文、呼び出し側指定の要求ヘッダ | 承認対象と束縛の定義が別に要る。次スライス |
| 返金・紛争処理・Provider の評価 | §7 で受容するリスクとして明記する |
| mainnet | testnet 限定を維持する |
| Provider の探索・比較 | Router の役割ではない |

## 5. 要件

### 5.1 入口と互換

- **FR-1**: quote に上流 URL を渡せる。**既存の `routeId` 指定の入出力・subject は変えない**。
  入口の形は設計で決める。
- **FR-2**: 動的 URL は**設定で明示的に有効にしたときだけ**受け付ける。既定は無効。
  **呼び出し側の入力や env の既定値から有効にならない**。

### 5.2 URL と束縛

- **FR-3**: 受け付ける URL は **https・userinfo なし・fragment なし**。長さに上限を設ける。
  IP リテラルのホストと既定以外のポートの扱いは設計で決め、決めた規則を試験する。
- **FR-4**: URL の同一性を**独自の正規化で決めない**。**1 つの直列化結果**を表示・保存・fetch・
  上流申告との照合のすべてに使う（既存コードは `new URL()` の結果を使っており、これを引き継ぐ制約とする）。
  クエリは**その文字列の一部として**許し、並べ替え・再エンコードをしない
  （事実 8 のクエリ拒否は動的経路では置き換える。**静的 route の拒否は維持**）。
- **FR-5**: quote 時に、検証済み URL・method・送信レール・選んだ上流 offer・受信条件・手数料・
  適用した資産ペアと設定の識別を**不変の記録として journal に保存**する。
  **purchase は保存した記録だけを実行**し、purchase の入力（呼び出し側が持ち回る quote 文書を含む）から
  URL・`payTo`・額を**組み立て直さない**。
- **FR-6**: 受信の支払いは**その quote に固有**に束縛する。**1 回の受信支払いが 2 つの送信を起こさない**。
  束縛は呼び出し側が書き換えられる**未署名の付随情報ではなく、署名または送金そのもの**に効いていること。
  発行していない束縛は従来どおり fail closed。
- **FR-7**: 同じ `(principal, requestId)` で**宛先（URL）が違えば衝突**として拒否する。
  静的 route と動的 URL の間でも同じ。
- **FR-8**: purchase 時、**Router が受信 settle・送信署名・broadcast のいずれかを行う前に**上流の offer を読み直し、
  保存した offer と一致しなければ**Router はどのレグも実行しない**。「一致」に含める項目（`scheme`・`network`・
  `asset`・`amount`・`payTo`・署名内容を決める `extra`）と、含めない項目（challenge ID・失効時刻など
  毎回変わるもの）を設計で列挙する。
  **これは「資金が動いていない」ことを意味しない**: MPP 受信では呼び出し側の送金が先に済んでいる（事実 16）。
  受信 settle の後にも上流が offer を変え得る（`orchestrator.ts:621-640`）。どちらも FR-10 で示し §7 で受容する。

### 5.3 承認の対象（D-1）

- **FR-9**: 動的 URL の承認 subject は少なくとも次を示す:
  **上流 URL の全体、method、送信側の `payTo`・network・asset・額、受信側の network・asset・受信額、
  その内訳（上流額と手数料）、両側の `decimals`、期限、`fundsMoveOnCredential`**。
- **FR-10**: subject は次を**構造化した値**で示す（文面だけにしない）:
  (a) 運用者はその宛先を確認していない (b) 支払い後にデータが得られなくても返金されない
  (c) `fundsMoveOnCredential` が真の経路では、**期限切れ・上流の変更・機能の無効化・予算切れ・運用者側の残高不足で
  Router が拒否しても、送った資金は戻らない**。
- **FR-11**: 示した値は FR-5 の記録と同一であること（表示だけ別に組み立てない）。
- **FR-12**: 静的 route の上流 URL は**従来どおりどの応答にも出さない**。
  動的 URL は**その quote の持ち主にだけ**返す（FR-32）。運用者向けログでの扱いは設計で決める。

### 5.4 受信条件と手数料（D-2）

- **FR-13**: 動的購入で使える `(受信 network・asset・レール) → (送信 network・asset・レール・scheme)` の組は
  **運用者が設定で列挙したものだけ**。各組は両側の `decimals`、**1:1 とみなす宣言**、手数料規則、
  1 件あたりの上流額の上限を持つ。列挙に無い offer しか出さない上流は quote を成立させない。
- **FR-14**: 上流が複数の offer を出すときの選び方は、**同じ offer 列・同じ設定・同じ署名能力に対して決定的**であること。
  推測で選ばない。FR-18 の範囲に入らない offer は**選ばない**。
- **FR-15**: 受信額は `上流額（両側の decimals で正確に換算）+ 手数料`。
  換算が割り切れない・桁あふれする場合は**拒否**する。手数料の丸めは**運用者有利の切り上げ**に固定する。
- **FR-16**: 手数料規則・資産ペア・上限は設定が権威で、**quote 時の値を FR-5 の記録に固定**する。
  これらの設定を変えたら、変更前の未処理 quote は purchase で拒否する
  （`routeconfig-fingerprint-design.md` の指紋照合と同じ扱いを動的購入にも適用する）。
- **FR-17**: 上流額が上限を超える、受信額が上流額を下回る、のいずれも quote を成立させない。

### 5.5 運用者の署名と支出の境界

- **FR-18（支払い操作の範囲）**: 運用者の鍵が行ってよい操作を**効果で**定義し、**署名・broadcast の前に**範囲外を拒否する。
  少なくとも: 設定した token（コントラクトと署名 domain の権威は**設定**であり上流ではない）、許す署名型、
  authorization の有効期間の上限、受取先は承認済みの 1 つ、**移転総額は承認済みの額ちょうど**、
  トランザクションに含めてよい call、手数料に使ってよい資産と上限、未対応の拡張・mode（MPP `pull` を含む）の拒否。
  **「保存した offer と一致する」ことは安全の根拠にしない**（最初から悪意ある offer は一致し続ける）。
- **FR-19（支出の上限）**: 動的購入による運用者の支出に**強制できる上限**を定める。数える対象は
  送信元本・**送信手数料（手数料資産を含む）**・失敗した送信・並行する予約・結果不明の送信。
  手数料の上限を rail が強制できる場合はそれを使う。強制できない残りは、
  **動的購入に割り当てた送信ウォレットの残高を明示的な最大損失として受容**し、その額を設定・運用手順に書く。
  既存の予算（事実 13）が手数料を数えていない点を前提にし、**「予算が差損を有界にする」とは主張しない**。
- **FR-20**: 送信側の残高不足を**受信 settle の前に**検出できる範囲で検出する。
  MPP 受信では呼び出し側の資金が既に動いているので、**この検査は呼び出し側を守らない**（FR-10 (c)）。

### 5.6 予算と、払わない相手

- **FR-21**: 購入の試行を **(1) 発行しただけの quote (2) 受信が成立しなかったと確定した試行
  (3) 結果が不明な試行 (4) 受信が成立した購入** に分け、予算の扱いをそれぞれ定める。
  **(1) と (2) は通算予算を恒久的に消費しない**。(3) は保守的に保持する（unknown で枠を復活させない）。
  「確定」の条件は rail ごとに設計で定める。
- **FR-22**: 動的購入の予算は**静的 route の予算と分離**し、動的側が尽きても静的 route は動く。
  尽きたときは明示的に失敗する。
- **FR-23**: 事実 14 は**現行の本番にも当てはまる**。動的 URL を本番で有効にする前に、
  **静的 route についても** FR-21 の (2) を満たす（この修正は本機能と独立に出せる）。

### 5.7 接続の安全（D-3）

- **FR-24**: 動的 URL への**すべての**接続（quote 時の読取、purchase 時の再読取、有料要求、SDK が内部で出す
  HTTP・RPC）は **SSRF 防御 A の transport を通る**。fixture 用の loopback 例外は動的経路に**適用しない**。
  B が入っていないホストで動的 URL を有効にしない運用条件を `DEPLOY.md` に書く。
- **FR-25**: A・B が扱わない宛先の方針を定める: **Router 自身の公開口**（Caddy・公開プロキシ経由を含む）、
  設定済みの **facilitator・RPC** を動的 URL の宛先にできない。運用者の静的 Provider を動的に指定することは
  許してよいが、その容量を守る（FR-30）。
- **FR-26**: リダイレクト無効、接続・応答全体の期限を動的経路でも保つ。
- **FR-27**: 上流から受け取るものすべてに上限を設ける: 402 の本文と**ヘッダ上の challenge**、復号後の
  offer の個数と保持する付随情報、有料応答の本文。超過は読み切らずに打ち切り、有料応答での超過は
  既存の終端（支払い済み・データなし）に写す。
- **FR-28**: **対応する応答の形を明示する**（content type・JSON の形）。対応外は「支払い済み・データなし」とし、
  その条件を FR-10 の開示に含める。呼び出し側に渡す付随情報は**検証済みの決まった項目**（例: content type）に限り、
  応答ヘッダ・例外文字列を素通ししない。
- **FR-29**: 上流の応答は**信頼しないデータ**として返す（指示として扱うべきでないことをツール結果の構造で示す）。
  `delivered` が示すのは「上流が成功の receipt と対応する形の応答を返した」ことであり、
  **チェーン上の確定や応答の正しさではない**ことを、返す結果で区別する。

### 5.8 匿名利用の乱用対策（D-3）

- **FR-30**: **未払いで起こせる仕事を有界にする**。対象は quote だけでなく **purchase の試行**
  （preflight・上流の再読取・受信 verify）を含む。送信元単位・全体・**宛先単位**の頻度と同時実行数に上限を設け、
  超過は外部接続の**前**に拒否する。宛先単位の上限は**ホスト名の別名で増やせない**こと。
  facilitator・RPC への正規の通信が動的 URL の負荷で止まらないこと。送信元の識別は設計で定める。
- **FR-31**: 入口で**要求の大きさと受信時間**を処理の前に制限する（事実 20）。
- **FR-32（持ち主の分離）**: **動的購入**では、quote を取った呼び出しだけがその quote の取得・purchase・
  status／結果の参照をできる。共有 principal（事実 10）と呼び出し側が選ぶ `requestId`（事実 11）、
  `paymentId`（事実 12）は**持ち主の証明にならない**。Router が quote 時に発行する推測不能な値の所持を
  持ち主の証明としてよい。再起動後も保つ。
  **静的 route の入出力は本スライスでは変えない**（FR-1）。静的 route に事実 11・12 が残ることは §7 に書く。
- **FR-33**: 未払い quote が journal・メモリ・起動時間に与える影響を有界にする（事実 21）。
  期限切れの未払い quote の保持と、その上限に達したときの挙動を定める。
- **FR-34**: 運用者が**再起動だけで動的 URL を止められる**。止めても静的 route は動く。
  止めたとき、発行済みの動的 quote は purchase で拒否する。

### 5.9 回帰

- **FR-35**: 静的 route の入出力・subject・公開射影は変わらない（FR-23 による予算の扱いの修正を除く）。
  動的購入の記録を含む journal を、**動的 URL を無効にした Router が再生できる**
  （起動でき、予算の消費と持ち主の分離が保たれ、動的 quote は実行されない）。

## 6. 受け入れ条件

**無課金の fixture**で検証する。受信の検証は**常に成功する stub ではなく**、オフライン署名と RPC fixture で
実際の検証経路を通す。fixture で示せるのは**拒否・束縛・会計・署名境界**であり、
**実際の決済・確定・手数料規則が費用を賄うこと**は示せない。それは別の testnet gate で確かめる（§9）。

| ID | 条件 |
|---|---|
| AC-1 | 無効（既定）のとき、URL 付き quote は**外部接続なしに**拒否される |
| AC-2 | 有効のとき、列挙済みペアの offer を出す上流 URL で quote → 承認 → purchase → delivered が成立する（x402→MPP、MPP→x402） |
| AC-3 | subject が FR-9・FR-10 の**全項目**（URL 全体・method・両側の network／asset／decimals・`payTo`・上流額・手数料・受信額・期限・`fundsMoveOnCredential`・未確認／返金なし／先行送金の表示）を含み、journal の記録と一致する |
| AC-4 | purchase に**改竄した quote 文書**（別 URL・別 `payTo`・別額）を渡しても、保存した記録が実行されるか拒否される |
| AC-5 | **元の署名／送金をそのまま**使い、未署名の付随情報だけを別 quote のものに差し替えた credential が拒否される。同額の quote 間、静的↔動的の間、並行、再起動後のいずれでも、**1 回の受信支払いで送信は高々 1 回** |
| AC-6 | quote 後に上流が FR-8 で列挙した**各項目**を変えると Router はどのレグも実行しない。列挙外の項目（challenge ID 等）の変化では成立する |
| AC-7 | 同じ `requestId` で URL が違えば拒否。静的 route との間でも拒否 |
| AC-8 | 列挙に無い network／asset／scheme しか出さない上流は quote 不成立。上限超の額も不成立 |
| AC-9 | decimals が異なるペアで割り切れない額は拒否。手数料は切り上げ |
| AC-10 | 手数料規則・ペア・上限の設定を変えると、変更前の quote は purchase で拒否される |
| AC-11 | http・userinfo・fragment・長すぎる URL を**外部接続なしに**拒否する |
| AC-12 | loopback・private・link-local・メタデータ宛て、**公開名が内部アドレスに解決する**場合を、動的経路の**全接続点**（quote 読取・再読取・有料要求・SDK の HTTP／RPC）で拒否する。fixture 能力の Router でも動的経路は loopback に届かない |
| AC-13 | Router 自身の公開ホスト名・設定済み facilitator／RPC を指す URL を拒否する |
| AC-14 | リダイレクトに従わない。期限超過で打ち切る |
| AC-15 | 上限超の 402 本文・challenge ヘッダ・offer 個数・有料応答本文を読み切らずに打ち切り、定義した終端になる。対応外の形（text・JSON 配列）と**偽の receipt** がそれぞれ定義した終端になる。journal の増分が上限内 |
| AC-16 | 範囲外の支払い操作（別 token／別 domain、長すぎる有効期間、複数受取先・分割、額の不一致、未対応 mode・拡張）を出す上流に対し、**署名も broadcast も起きない** |
| AC-17 | rate limit: 送信元単位・全体・宛先単位（**別名を使っても**）で、quote と purchase 試行の超過分が**外部接続なしに**拒否される。大きすぎる・遅すぎる要求本文が処理前に切られる |
| AC-18 | **無効な署名の credential を繰り返し出しても通算予算が減らない**（静的 route・動的の両方）。結果不明の試行は枠を保持する |
| AC-19 | 動的側の予算を使い切っても、静的 route の purchase は成立する |
| AC-20 | 持ち主でない呼び出しが、**`quoteId`・`requestId`・`paymentId` を知っていても**、動的 quote の取得・purchase・status／結果の参照をできない。再起動後も同じ |
| AC-21 | 未払い quote を上限まで発行しても、journal・メモリ・起動時間が定めた上限内 |
| AC-22 | 動的購入を含む journal を無効の Router が再生でき、予算が保たれ、動的 quote は purchase で拒否される |
| AC-23 | 静的 route の既存テストが全通過する（skip と失敗を区別して報告） |
| AC-24 | 上流の応答が「信頼しないデータ」の印と、`delivered` が示す範囲の区別を伴って返る |

fixture の各 AC は**壊して落ちることを確かめる**。複数の独立した防御で守られる性質は、
それぞれを外したときに対応する試験が落ちることで確かめ、運用上の gate（B の導入確認など）は対象外とする。

## 7. 受容するリスク（明記する）

| リスク | 扱い |
|---|---|
| **悪意ある Provider**（代金を受け取り無価値な応答を返す） | 呼び出し側が負う。FR-10 で示す。Router は応答の価値を判断しない |
| **支払い済み・データなし**（受信成立後に送信が失敗・不明・上流が条件を変更） | **返金しない**（testnet）。FR-10 で示し、証跡は journal に残す。返金の設計は mainnet の前提条件 |
| **MPP 受信で、Router が拒否する前に呼び出し側の資金が動いている** | Router は防げない。FR-10 (c) で**credential を作る前に**示す |
| 送信手数料・失敗送信による運用者の差損 | FR-19 の上限まで。最終的な上限は**動的用に割り当てたウォレット残高** |
| 受信資産が溜まり送信資産が減る偏り | 補充は運用者の手作業。尽きたら動的購入は明示的に止まる |
| 1:1 とみなした資産ペアの乖離 | testnet 限定の間は受容。**mainnet では D-2 を見直す** |
| 予算の枯渇によるサービス停止 | **払った購入によるもの**は安全装置として受容。**受信が成立しなかったと確定した試行による恒久的な消費は受容しない**（FR-21〜23）。**結果不明の試行は枠を保持し続ける**ので、受信の検証先が応答しない状況を作れる相手による停止は残る（枠を解放して解消しない） |
| 静的 route の quote／結果が `requestId`／`paymentId` を知る相手に読める | 現状維持。`paymentId` は Router が生成する UUID だが、**`requestId` は呼び出し側が選ぶ値で、推測も選択もできる**。読めるのは公開 route の quote と公開データ。動的購入には持ち込まない（FR-32） |
| 公開サービスへの負荷の踏み台 | FR-30 で頻度を抑えるが、ゼロにはできない |
| Router を経由した支払いの匿名性・規制上の論点 | testnet 限定の間は扱わない。mainnet の前提条件 |

testnet の資産に市場価値が無くても、**ウォレットの残高・faucet の入手量・ホストの資源は有限**であり、
上の差損と枯渇は運用を実際に止める。
