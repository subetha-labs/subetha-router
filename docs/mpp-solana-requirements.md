## 0. 背景: なぜ今 Solana の MPP か

2026-10-08 の第三者 Provider の検証（`docs/DEPLOY.md` §2c の記録の後）で分かったこと:

- Solana devnet で **x402 v2** を出す第三者 Provider は、価格が動的の上限内のものが 1 件だけで、それも非標準の `extra.paymentFlow` を持ち候補外だった。
- **pay.sh**（API provider を束ねる gateway）は x402 ではなく **MPP の `method="solana"`** で払わせる（未払いの GET で見た challenge: `method="solana"`、`intent="charge"`、`request` に `amount`・`currency`（USDC の mint）・`methodDetails{decimals, feePayer, feePayerKey, network, recentBlockhash, tokenProgram}`・`recipient`。
  本番は Solana mainnet、sandbox は "localnet"）。
- Router が **MPP で Solana を受け取る**（S-5）・**MPP で Solana の Provider に払う**（S-6）の両方を持たないと、この形の Provider に届かない。「Solana の Provider の大半が MPP」とは**言えない**（走査は discovery の一覧だけ）。本書の動機は owner の指示と、観測した 1 件の gateway の形。

### 1.1 設計の初めの再確認（2026-10-08。`@solana/pay-kit` 0.13.1 の実物。第 6 版）

確かめ方: pay-kit の server（`createPayKit` + `pay.fetch`）を loopback の http server に包み、pay-kit の client（`createPayKitClient().fetch(url, init, "mpp")`）で Solana Foundation の localnet sandbox RPC に対して pull（`operator.feePayer: true`）と push（`false`）を 1 回ずつ流して challenge と credential の wire を記録し、配布物の source（server の `verify`、client の `charge`）を読んだ。
**端から端までの成功は観測していない**（pull は demo 鍵を operator と payer の両方に使ったため server の規則「fee payer は転送の authority になれない」で拒まれ、push は sandbox の合成 blockhash で `Blockhash not found`）。従って以下は「wire の形」と「source の規則」の事実で、成功経路の確認は AC-15・AC-16 の fixture が最初になる。記録（script・wire の log）は private の作業記録に置く。

## 2. 今の Router が持つもの（本書の基準 `ed60794`、2026-10-08。リポジトリの事実）

- **受信の MPP は Tempo 専用**: `src/adapters/inbound/mpp.ts` は `mppx/server` の `Mppx.create` + `tempo.charge`、**push 固定**（`supportedModes: ["push"]`）、challenge の HMAC 束縛鍵は注入（ホストの `SUBETHA_MPP_INBOUND_SECRET` を入口が内部 env `ROUTER_MPP_INBOUND_SECRET` で子に渡し、`src/config.ts` が注入値を**解析**する。`src/` が process の env を直接読むことはない）。**credential は preflight で発行 offer に束縛**: `payload.challengeNonce` = offer の nonce、`accepted` = 保存した offer と完全一致、route binding、期限、wire の中の challenge id = nonce（`:286-310`）。verify は SDK、settle は `rejected`（`source_rejected`）／`unknown`（`source_settle_unknown`）／`settled`（`txRef`）。
- **送信の MPP も Tempo 専用**: `src/adapters/outbound/mpp.ts`（静的）・`mpp-dynamic.ts`（動的）は `mppx/client` の `tempo.charge`、push 固定（こちらで送金して hash を渡す）、動的は許可した欄だけの challenge と組み直しの署名 facade。**結果の表**: 送出前の失敗は `not_sent`（理由は列挙）、送金 RPC の委譲の後の失敗は `unknown`（`destination_pay_unknown`）、**領収なしの応答は 4xx でも `unknown`**（送金済みのため）、領収が照合できなければ `unknown`（`destination_receipt_unverified`）、整合した領収つきの非 200 は `paid_no_data`（**静的は 502 だけ** `mpp.ts:630-660`、**動的はすべての非 200** `mpp-dynamic.ts:1115-1117`）、200 は `paid`。動的の手数料は `FeeEstimate`（EVM の gas の欄）と `feeAsset`（= 宛先の資産。`src/config.ts:273-275`、`:808`）で Tempo 前提。core は **プロファイルに `maxFee` があるときだけ** `estimateFee` を呼ぶ（`src/core/dynamic.ts:270`）。受信の verify で `isValid: false` は `verify_failed`、RPC の失敗は `source_verify_unavailable`（`src/core/orchestrator.ts:645-656`）。再起動時に `source_settled` の intent は `paid_undelivered`（`interrupted_at_restart`）で終端し、送信を再開しない（`src/core/store.ts:395`）。
- **Solana は x402 だけ**: 受信は facilitator に verify/settle を委ね、`checkSvmTransaction`（`src/adapters/inbound/x402-svm.ts`）が **Router が受け取る唯一の形**（version 0、lookup table 無し、命令はちょうど 4 つ = SetComputeUnitLimit・SetComputeUnitPrice・TransferChecked・Memo、署名 2 つで fee payer の署名は空）を byte 一致で検査する。送信は Router が同じ形の message を組み、builder に依存しない検査、署名前の hash の予約、署名の検証、送出前の wire の再検査（`src/adapters/outbound/x402-svm.ts`）。鍵は専用の ed25519 `SUBETHA_OUTBOUND_SOLANA_KEY`（devnet USDC の ATA あり。**SOL は無い**）。受取は `SUBETHA_SOLANA_RECEIVER`（ATA あり）。RPC は guarded transport（設定の URL だけ。loopback 拒否）、受信の起動時の検査と送信の blockhash・残高で使い、方法と回数は列挙して固定。
- **payer の道具**: `npm run sign`（`tools/sign-payment.ts`）は offer から rail を判定し、Solana の鍵は **`SOLANA_PAYER_PRIVATE_KEY`**（`wallet:new:solana` が出す。案内は「**SOL は要らない**」= x402 の facilitator が手数料を払う前提）。
- **レール**は `"x402"` / `"mpp"` と network の組で合成。MPP の能力は `mppTempo` の 1 つ。有効化は公開の定数 `RAILS_ACTIVATION`（方向別）で、入口はその値を**内部の env**（`SUBETHA_RAILS_ACTIVATION`）で子に渡す（親の env からは変えられない）。journal・予算（`(network, asset)` の区分）・開示・SIGKILL の中断試験は既存。

## 3. 範囲

- **S-5 受信 = Solana の MPP**: 呼び出し側が Solana devnet の USDC を MPP（`method="solana"`、`intent="charge"`、**push**）で Router に払い、Router が既存の送信レールの Provider から買って届ける。
- **S-6 送信 = Solana の MPP**: MPP の `method="solana"` でしか受け取らない Provider に Router が Solana devnet の USDC で払う（**pull = 相手が fee payer** を主、**push = Router が手数料を払う** は D-23）。
- 範囲外: mainnet、`session`・`subscription`・confidential・`splits`、Token-2022、native SOL での支払い、自動 swap/bridge、同レール同チェーン（MPP Solana → MPP Solana。D-16）、pay.sh の mainnet 利用、受信の pull（D-18）。

## 4. 機能要件

### 4.1 共通

- FR-39 **レールの表現**: MPP を network 別の能力にする（x402 の S-3 と同じ形）。受信は `mppInbound` を `{ tempo, solana }` に、送信は `MppTempoCapability` に加えて **`MppSolanaCapability`** = `SvmSigningCapability` と同じ「message の bytes の写しにだけ同期で署名する能力」（鍵は D-19）。route／プロファイルは `rail` と `network` の組で引く。既存の Tempo の経路は 1 つも変えない（AC-15 の回帰）。
- FR-40 **有効化**: `RAILS_ACTIVATION` に方向別の **`solanaMpp: { inbound, outbound }`** を足す（既存の `solana` = x402 と独立）。既定 `false`。公開の定数で決まり、親の env からは変えられない（内部 env の transport は既存のまま）。
- FR-41 **network の束縛**: challenge の `methodDetails.network` は **`"devnet"`** だけを受ける／出す。`currency` は表の devnet USDC の mint、`tokenProgram` は表の Token program、`decimals` は 6。表に無い値は受信では発行せず、送信では候補外。識別子の比較は**大文字小文字を区別**する（base58）。
- FR-42 **ID と開示**: route／プロファイル ID は既存の名前空間（例: 受信の静的 `md-x402-eth-snapshot-solmpp`・`md-mpp-eth-snapshot-solmpp`、送信の静的 `md-solmpp-eth-snapshot`、動的 `dyn-solmpp-to-x402` / `dyn-solmpp-to-mpp` / `dyn-x402-to-solmpp` / `dyn-mpp-to-solmpp`。確定は設計）。`subject` の `fundsMoveOnCredential` は受信 MPP Solana で `true`（**保守的な開示**。`type="signature"` の payer は credential の時点で送金済み。`type="transaction"` では資金が動くのは Router が purchase で送出する時点だが、Router は payer がどちらの型を出すか事前に知らないので route の開示は `true` のまま。型ごとの違いは CLAUDE.md に書く。D-29）。
- FR-43 **予算**: Solana devnet USDC の区分は既存の `(network, asset)` に**合算**（受信 x402 Solana・送信 x402 Solana・本書の受信・送信の 4 つが同じ区分。D-14）。**x402 Solana ↔ MPP Solana の組は両レグが同じ区分を使う**ので、1 件の上限と通算の両方が両レグ分で効くことを試験する（AC-15）。
- FR-44 **手数料の方針（pull・push の両方）**:
  - **価格づけ（明示の例外）**: 今の code は **MPP の宛先に `feeAsset`・`maxFee` を必須**にし（`feeMargin` は省略時に既定値。`src/config.ts:778-786`）、**MPP の全プロファイルで quote ごとに gas を見積もって cap を決める**（`src/core/dynamic.ts:339-345`。`maxFee` が無ければ失敗）。これは Tempo（EVM の gas）の規則なので、**宛先が `solana:` の MPP プロファイルを明示の例外**にする: (a) 設定は `feeAsset`・`maxFee`・`feeMargin` を**持たないことを要求**（あれば `ConfigError`）、(b) 動的 core はこの宛先では `estimateFor` を呼ばず cap を持たない quote を作る（`pricing` に `maxFee`・`estimate` を出さず、`fee_too_high` は起きない）、(c) purchase／store／replay は cap の無い MPP の quote をこの宛先に限って受ける（Tempo の quote に cap が無ければ従来どおり拒む）。手数料は規則の手数料（flat/bps/min）だけ。この例外は設定の生成・読み込み・core・store のそれぞれで試験する（AC-16）。
  - **pull**: Router は手数料を払わない（fee payer は相手）。SOL の勘定は無い。
  - **push**（D-23 の第 2 段）: 手数料の資産は SOL（lamports）で、USDC の予算とは**別の勘定**（lamports と USDC の base units を比べない・合算しない）。1 購入の上限は**定数** = base fee 5,000 lamports × 署名数 + `ceil(priority price [micro-lamports/CU] × compute limit [CU] / 1,000,000)` lamports（`SetComputeUnitPrice`・`SetComputeUnitLimit` は固定値）。**journal に lamports の区分を持ち**、署名の前に 1 購入分を**原子的に予約**し、通算の上限（定数）を超えれば `not_sent`（`budget_exhausted`）。Router の送信鍵の SOL 残高を purchase ごとに 1 回読み（`getBalance`）、「予約済み + 上限」未満なら受信の verify の前に `operator_funds_unavailable`。手数料は運用者が負担し quote の額に転嫁しない。

### 4.2 受信（S-5）

- FR-45 **受ける credential の型は 2 つ。Router は手数料を払わない**（D-18 の結論は維持、機構は §1.1 F-1・F-2 で訂正。D-28）: challenge は `feePayer: false`（`feePayerKey` 無し）、`recentBlockhash` は**出さない**（payer が自分で取る。出すと期限の管理と「相手の値を信じる」問題が生じる）、`splits` 無し、`request.externalId` を出す（FR-46）。credential は (a) **`type="transaction"`**（payer が fee payer として**全署名**した tx の base64。Router が検査してから **Router の RPC で送出**し、確定を待つ。pay-kit の client の既定）と (b) **`type="signature"`**（payer が送出・確定済みの署名の base58。pay-kit の `broadcast: true`）。どちらも fee payer は payer で署名はちょうど 1 つ。Router が fee payer になる形（sponsorship、`feePayer: true`）は**持たない**。(a) で Router が送出することは**資金の移動の実行**なので、送出は intent ごとに 1 回（同じ intent への再提示は既存の終端の読み返し。AC-20）、送出の前に拒めても **payer が自分で送出していないとは限らない**（同じ bytes なら二重の転送にはならないが、未送金の証明にはならない。FR-48）。
- FR-46 **challenge の発行と承認値への束縛**: `mppx` の `Method.from` で Solana の charge の schema を定義し、既存の Tempo 受信と同じ `Mppx.create` + HMAC 束縛（注入した秘密）で発行する。`recipient` は `SUBETHA_SOLANA_RECEIVER`（owner の公開鍵。ATA は配備済み。起動時に ATA の存在・owner・mint を確かめる = 既存の受信 x402 Solana と同じ検査）。`amount` は quote の額、`currency`・`network`・`decimals`・`tokenProgram` は FR-41。**`request.externalId` は challenge ごとに Router が作る一意の値**（16 バイト以上の乱数を base58。`request` の一部として HMAC の入力に入る = 改竄できない。offer の `extra` に写しを持ち、Memo の照合に使う。FR-47。challenge の `id` は `request` を含む HMAC なので `externalId` に `id` は使えない。§1.1 F-3）。**preflight は Tempo 受信と同じ 5 点**（`payload.challengeNonce` = 発行 offer の nonce、`accepted` = 保存した offer と完全一致、route binding、期限、wire の中の challenge id = nonce）に加えて `payload.type` が `"transaction"` か `"signature"` であることと型ごとの形（`transaction`: base64 で復号後 1232 バイト以下。`signature`: base58 64 バイト）、そして **wire の credential に埋め込まれた challenge の全欄（`request`・`methodDetails`・`expires`・`opaque`）を HMAC で検証**（mppx の server の検証をそのまま使う。id の写しだけでは足りない）。HMAC は challenge の改竄を防ぎ、**購入への束縛は preflight の一致検査**が担う。**Router は SDK の server 実装（pay-kit）を本番コードに入れない**（D-20）。
- FR-47 **検証は Router 自身が**（層を分ける: preflight → verify → settle。型で RPC の有無が違う）:
  - **共通の形**（どちらの型でも tx に要求。`checkSvmTransaction` の **primitives**（命令の復号、`TransferChecked` の欄、Memo の欄、口座の役割）を再利用し、形は別に定義する。x402 の検査は変えない）: version 0、lookup table 無し、**署名はちょうど 1 つ**（`staticAccounts[0]` = fee payer = payer = 転送の authority = source ATA の owner）、命令は compute budget（`SetComputeUnitLimit`・`SetComputeUnitPrice` を**それぞれ高々 1 つ、順序は問わない**（pay-kit の client は price → limit、Router の x402 は limit → price。§1.1 F-4）、limit ≤ 200,000、price ≤ 5,000,000 micro-lamports/CU、他の compute-budget 命令は不可）・**`TransferChecked`**（program = 表、mint = `currency`、decimals = 6、額 = challenge の `amount`、宛先 = `recipient` の**導出 ATA**、source = 署名者の導出 ATA、authority = 署名者）・**Memo がちょうど 1 つで中身が challenge の `request.externalId` と byte 一致**（D-22 の機構の訂正）、それ以外の命令は無い（ATA の作成も不可）。
  - **verify、`type="transaction"`（RPC を呼ばない）**: 復号し、共通の形を検査し、**署名を message に対して ed25519 で検証**（公開鍵 = `staticAccounts[0]`）。blockhash は検査しない（使えなければ送出の preflight で落ちる）。時刻の条件は purchase 時点の preflight の期限（Router は offer の期限内にだけ送出する）で、`blockTime` は見ない。形違い・検証失敗 → `isValid: false`（core の **`verify_failed`**。Router は送出していない）。
  - **verify、`type="signature"`**（RPC が答えなければ既存の `source_verify_unavailable`）: 設定の Solana RPC（guarded transport）で `getTransaction(signature, { commitment: "confirmed", maxSupportedTransactionVersion: 0, encoding: "base64" })` を **1 回**（`null` = 見つからない → `isValid: false`。`finalized` は待たない。D-21）。transaction と meta を読み、共通の形に加えて**署名の bytes が credential の署名と一致し、message に対して ed25519 で検証できる**こと（RPC が返した = 含まれた、だけに頼らない）、`meta.err` が `null`、`blockTime` が challenge の発行〜期限の内（`null` なら不正）、`slot` が有ること。応答の大きさ・時間は既存の RPC の上限（64 KiB・10 秒）。
  - **settle、`type="transaction"`**（資金が動く段。順序を固定する。送出は intent ごとに 1 回）: (1) 署名（= tx の署名 [0]）が journal の消費済み集合に無いこと（有れば `rejected`、`source_rejected`）。(2) `sendTransaction`（base64、`skipPreflight: false`、`maxRetries: 0`）を **1 回**。(3) 応答が RPC の error なら `getSignatureStatuses([署名], { searchTransactionHistory: true })` を **1 回**: `confirmed` 以上で `err` 無しなら (5) へ（既に chain 上にあった = payer 自身が送出済み）。`confirmed` 以上で `err` ありなら `rejected`（`source_rejected`。USDC の転送は実行されていないが、**SOL の手数料は引かれ得る**）。見つからない・`processed`・形違い・RPC の失敗なら (4) へ（**1 回の不在は未送出の証明にならない**: 伝播の遅れや payer 自身の先の送出があり得る）。応答が無い（transport の失敗・期限）なら (4) へ。(4) `getSignatureStatuses` を 2 秒間隔で**経過時間 30 秒**まで（回数は高々 15。各要求の期限は残り時間で切る。`processed`・形違い・RPC の失敗は続行）: `confirmed`／`finalized` で `err === null` → (5)。`confirmed` 以上で `err` あり → `rejected`（上と同じ）。期限まで見えない → `unknown`（`source_settle_unknown`。送出されたかもしれない。**preflight の失敗で終わった場合も `unknown`**: Router は「自分が送出していない」ことしか知らず、未送金は証明できない）。(5) **`source_settled` の journal 行そのもの**（`txRef` = 署名）を消費の記録として書く（別の行にしない。記録と確定の間に crash の窓を作らない）。失敗 → `unknown`（`source_settle_unknown`）。`getTransaction` は呼ばない（送った bytes を Router 自身が検査済みで、署名が tx を一意に定める）。
  - **settle、`type="signature"`**（RPC は呼ばない）: 消費済み署名の記録（SR-M2）に成功したら `settled`（`txRef` = 署名）。既に消費済みなら `rejected`（`source_rejected`）。記録に失敗したら `unknown`（`source_settle_unknown`）。消費の記録は `transaction` 型と同じく `source_settled` の行そのもの。replay の判定はどちらの型も journal の `source_settled` の `txRef` の集合から復元する。
- FR-48 **受信の結果の表**（`rejected` は「Router は受けない」。資金が動いているかは**型と段で違う**: `signature` 型の payer は credential の時点で送金済み、`transaction` 型は Router の送出より前の拒否なら **Router は送出していない**（payer が自分で送出していなければ未送金だが、Router はそれを証明できない））:

  | 段 | 型 | 事象 | 結果 |
  |---|---|---|---|
  | preflight | 両方 | nonce・accepted・route binding・期限・wire の id・`type`・型ごとの形のどれかが違う | `rejected`（既存の理由 `nonce_mismatch` 等。`signature` 型は送金済み = 開示どおり返金なし。`transaction` 型は Router は送出していない） |
  | verify | `transaction` | 復号できない・共通の形と違う・Memo が `externalId` と違う・額・mint・宛先が違う・署名が検証できない | `isValid: false` → core が **`verify_failed`**（Router は送出していない） |
  | verify | `signature` | RPC 不達・形違い・上限超え | `unknown`（`source_verify_unavailable`。再試行しない） |
  | verify | `signature` | transaction が無い（`null`）、`err` あり、共通の形と違う、署名が検証できない、Memo が違う、額・mint・宛先が違う、期限外 | `isValid: false` → core が **`verify_failed`**（settle に進まない） |
  | settle | 両方 | 署名が既に消費済み（replay。別の購入か同じ購入の再送） | `rejected`（`source_rejected`） |
  | settle | `transaction` | 署名が `confirmed` 以上で chain 上に `err` つきで見える | `rejected`（`source_rejected`。USDC の転送は実行されていない。SOL の手数料は引かれ得る） |
  | settle | `transaction` | 送出の応答が RPC の error（preflight の失敗を含む）または無応答で、経過時間 30 秒の追跡でも署名が `confirmed` 以上で見えない（`processed` のままを含む） | `unknown`（`source_settle_unknown`。Router は送出していないか、送出されたが見えない） |
  | settle | 両方 | 消費済みの記録（journal）に失敗 | `unknown`（`source_settle_unknown`） |
  | settle | 両方 | 記録できた（`transaction` 型は `confirmed` 以上で `err` 無しの後） | `settled`（`txRef` = 署名）→ 送信へ |

## 5. 安全要件（先行の 2 文書の SR-1〜SR-7 を引き継ぐ。本書は `SR-M`）

- SR-M1 **RPC の上限**: 受信の verify は `signature` 型で `getTransaction` 1 回、`transaction` 型は RPC 無し。受信の settle は `transaction` 型で `sendTransaction` 1 回 + `getSignatureStatuses` 最大 16 回（error の応答の後の 1 回を含む。2 秒間隔、**経過時間 30 秒**で打ち切り、各要求の期限は残り時間で切る）、`signature` 型は RPC 無し。送信は `getLatestBlockhash` 1 回・`getTokenAccountBalance` 1 回・（push）`getBalance` 1 回・`sendTransaction` 1 回・（push の確定）`getSignatureStatuses` 2 秒間隔で最大 15 回・（pull の領収）`getTransaction` 1 回、起動時／purchase ごとの宛先 ATA の `getAccountInfo` 1 回。方法はこれだけ。応答は 64 KiB・10 秒。すべて guarded transport（設定の RPC だけ、loopback 拒否）。`sendTransaction` は**再試行 0**（`maxRetries: 0`、preflight あり）。`npm run sign` の方法は `getLatestBlockhash` 1 回だけ（送出しない。D-29）。
- SR-M2 **二重払いと replay の永続化**: 送信は message hash の予約（FR-37。静的・動的で**同じ台帳**、署名の前に原子的に永続化、並行の 2 件は後の方が `collision`、process の中断後の再起動で予約が残り `unknown` として確定、再送信 0）。受信は **消費済み署名の集合を journal に永続化**（`source_settled` の行の `txRef`。同じ署名の並行 2 件は後の方が `rejected`、再起動後も拒む、保持期間は journal と同じ = 削除しない）。発行済みの challenge は既存の quote の台帳（journal）から復元する。再起動時に `source_settled` で止まっていた intent は既存どおり `paid_undelivered`（`interrupted_at_restart`）で終端し、**送信を再開しない**。 `transaction` 型の受信で Router が送出するのは intent ごとに 1 回（intent の lock。別の intent に同じ tx を出しても Memo の `externalId` が違うので verify で先に落ち、送出に至らない）。
- SR-M3 **鍵の境界**: 受信に署名鍵は無い（HMAC の秘密だけ。既存の注入）。送信の署名は `SvmSigningCapability` の形（bytes の写しにだけ署名、鍵の文字列を保持しない）。`src/` は process の env から秘密を読まない（注入値の解析は既存のまま）。
- SR-M4 **fee payer の隔離**（pull。FR-35 の除外をすべて引き継ぐ）: `feePayerKey` は運用者の集合に無く、Router の鍵・Router の ATA・`recipient`・宛先 ATA・mint・Token program・System program・compute-budget program・Memo program のどれとも違う。Router の署名は [1] だけで、[0]（fee payer）は空のまま送る。wire の再検査で [0] が空・[1] が自分の署名・message が予約と一致。
- SR-M5 **固定の失敗**: Provider／RPC／payer の文言を転送しない（既存の規則）。
- SR-M6 **依存の向き**: `@solana/pay-kit` は `src/`・`tools/` から import しない（`@x402/svm` と同じ。fixture と試験だけ）。`mppx` の version は Router 側で 1 つ（D-25）。

- AC-19（agent の手順）: `npm run sign` が MPP Solana の offer で `SOLANA_PAYER_PRIVATE_KEY` から `type="transaction"` の credential を作り、**送出しない**（fixture の RPC で `getLatestBlockhash` 1 回だけ、`sendTransaction` 0 回）、署名前の拒否（network・資産・期限・額・`feePayer: true`・`externalId` 無し・`splits`）、再実行は別の署名を出すが送出しない、鍵を出さない。credential を Router（fixture の RPC）に出して `settled` になる（道具と受信の往復）。
- AC-20（中断）: 受信は（`transaction` 型）送出の前・送出の後で行の前・行の後、（`signature` 型）行の前後、送信は予約の後・署名の後・送出の前で SIGKILL → 再起動で表どおり（受信: 行の前なら `unknown`（`interrupted_at_restart`。`transaction` 型で送出前でも Router は未送金を証明できず、区別しない = 既存の規則）、行の後なら既存どおり **`paid_undelivered`**（送信は再開しない）、**同じ intent**（同じ `paymentId`・`requestId`）への再提示は既存どおりその intent の現在の終端を返す（`src/core/orchestrator.ts:520`、新しい購入を始めない）。**別の intent** で同じ署名を出せば、消費の行の有無に**関わらず** `rejected`: 古い credential は新しい intent の preflight（nonce・accepted・wire の中の challenge id）で落ち、新しい challenge に古い署名／tx を包み直しても transaction の Memo（古い challenge の `externalId`）が verify の Memo 検査で落ちる（`verify_failed`。`transaction` 型なら送出に至らない）。行が有れば settle の消費済み検査でも落ちる。つまり 1 つの payer の transfer は、それを発行した intent にしか使えない。送信: `unknown`、再送信 0、同じ message は `collision`）。
- AC-21（sabotage と独立レビュー）: 先行文書と同じく、各 PR に変異の表と Codex のレビュー。SR-3 と同じ署名の境界の独立レビューを **2 回**（送信の adapter の PR と、統合の PR で実ソース全体）。
