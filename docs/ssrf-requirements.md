# 要件: SSRF 防御（段階 0 / 1 / 2）

> 2026-10-01。`generalization-requirements.md` §15.2 の FR-8''' が「警告のみ」と縮小したのは、
> **上流 URL が設定値であり攻撃者が注入できない**ためだった。
> owner が「AI が上流 URL を指定する」方向を検討しているため、その前提が崩れる場合に
> 何が必要かを**段階ごとに**定める。段階 0 はコード変更なし。

## 1. 脅威の定義（何を守るか）

SSRF は「**Router の立場で任意の URL へ到達させる**」攻撃である。被害は**到達そのもの**であり、
支払いでも応答本文でもない。したがって次の 2 つでは**防げない**（実測で確認済み）:

| 案 | 守れるもの | 守れないもの |
|---|---|---|
| 402 を確認した先にしか払わない | 誤った支払い | 到達は fetch 時点で起きている |
| 上流の本文・例外文字列を返さない | 本文の漏洩 | **応答時間**（0ms / 15ms / 5000ms が区別できる）と **GET の副作用** |

両方とも**既に実装済み**（`redirect: "error"`、`SAFE_REASONS` 許可リスト）。
残るのは**fetch の前に止める**層だけである。

## 2. 事実（デプロイ先と実装の現状）

| 事実 | 出所 |
|---|---|
| コンテナは既定 bridge ネットワーク（`--network` 指定なし） | `DEPLOY.md:46` |
| IMDSv2 の強制は**ドキュメントに記載なし**（= AWS 既定の v1 許可が残り得る） | `DEPLOY.md` 全体 |
| Router 自身は IMDS を**使わない** | `grep` で参照 0 件 |
| 上流への `fetch` は **6 箇所**（素の `globalThis.fetch`、`undici` 非依存） | 実測 |
| quote の失敗は即返り、**レート制限なし** | `orchestrator.ts:305,317,379` |
| 合成 fixture は **loopback を要する** | `config.ts:99` |

## 3. 4 層の防御と、各層が止める攻撃

| # | 防御 | 止める攻撃 | 状態 |
|---|---|---|---|
| 1 | fetch 前のアドレス範囲検査（**DNS 解決後**） | 内部アドレスの直接指定、`evil.com → 10.0.0.5` の解決 | **未実装** |
| 2 | 接続時のアドレス固定 | DNS rebinding（検査と接続の間に答えを変える） | **未実装**（`undici` 依存が要る） |
| 3 | リダイレクト禁止 | 302 で内部へ飛ばす | 実装済み |
| 4 | 本文・例外文字列を出さない | 到達後の内容漏洩 | 実装済み |

**#1 だけでは #2 の攻撃に負ける。** ただし #1 が直接指定の攻撃を全て止め、
#2 が守るのは攻撃者が自前 DNS を持つ場合に限られる。優先順位は #1 > #2。

## 4. 段階と要件

### 段階 0: インフラで IMDS 経路を塞ぐ（コード変更なし・**今やる**）

**FR-0a**: `DEPLOY.md` に IMDSv2 の強制を追記する。
`HttpTokens=required` に加え **`HttpPutResponseHopLimit=1`** とする。

理由: hop limit 1 なら、**コンテナ（ホストから 1 hop 先）からメタデータに届かない**。
Router は IMDS を使わない（§2）ので、塞いでも Router は困らない。
これで **最も危険な標的（IAM 認証情報）が #1 の実装前に消える**。

**FR-0b**: §9 の「EC2 側で必要なこと」に置く。既存の記述（SG・TLS・鍵）と同列の
**範囲外事項**であり、Router の挙動を変えない。

**受け入れ条件**: AC-0 — 手順が `aws ec2 modify-instance-metadata-options` の
具体的なコマンドとして書かれ、**確認コマンド**（現在値の読み出し）を伴う。

### 段階 1: fetch 前のアドレス検査（**「AI が URL を指定する」機能を採用する時点で必須**）

**FR-1a**: `real` モードの上流 fetch（6 箇所）に限り、**fetch 直前に hostname を DNS 解決**し、
返った**全アドレス**を検査する。1 つでも次に該当すれば **fetch しない**:
loopback、private（10/8, 172.16/12, 192.168/16）、link-local（169.254/16, fe80::/10）、
ULA（fc00::/7）、IPv4-mapped IPv6、`::1`、unspecified（0.0.0.0, ::）。

**FR-1b**: `synthetic` モードは対象外（fixture が loopback を要する）。

**FR-1c**: 拒否は**ネットワーク要求の前**であること。拒否の理由は固定コードで、
解決したアドレスを応答・journal・ログに**出さない**。

**FR-1d**: **DNS rebinding は防げない**ことを明記する（受容ではなく段階 2 の課題）。

**FR-1e**: `undici` を依存に**足さない**。既存の `fetch` 呼び出しの前段に同じ検査を置く。

### 段階 2: 接続時のアドレス固定（**段階 1 と同じ PR で入れる**）

**FR-2a**: `undici` を依存に追加し、解決済みアドレスへの接続を `dispatcher` で強制する。
検査したアドレス以外に接続しない。

**FR-2b**: 段階 1 と**分けない**。分けると「機能だけ先に出て rebinding に開いた期間」ができる。

## 5. 段階 1・2 に進む条件（判断は owner）

「AI が上流 URL を指定する」機能を採用する判断と**セット**で着手する。
採用しないなら段階 0 だけで脅威自体が存在しない。

採用の価格: 段階 1 + 2 + `undici` 依存 + 6 箇所の配線 + fixture との分離。
得られるもの: 設定への追記と再起動を省ける。

## 6. 本書で決めていないこと

段階 1・2 の着手時期。`undici` の版。検査を adapter ごとに置くか共通関数にするか（設計で決める）。

### 7.2 要件の構造を変える: **不変条件を先に、実現手段は選択**

従来は「段階 1・2 が必須」と**実装を規定**していた。これは不要な制約だった。

**INV-1（不変条件）**: 「禁止された宛先に Router が**接続できない**」。
DNS rebinding を含めて、**接続時点で**保証されること。

これを満たす手段は 2 つあり、**どちらか**を選ぶ（併用も可）:

| 手段 | 内容 | 守れる範囲 | 代価 |
|---|---|---|---|
| **A. アプリ側** | fetch 前の DNS 解決 + 範囲検査 + **解決済みアドレスへの接続固定**（`undici` dispatcher） | Router の発する全 HTTP | 10 経路への配線、`undici` 依存、fixture との分離 |
| **B. インフラ側** | `DOCKER-USER` チェーンの egress 規則、または**迂回不能**な forward proxy（CONNECT の宛先も検証） | コンテナの全 egress（**アプリのバグも含めて**） | 展開手順・検証手順。IPv4/IPv6・host 宛て・コンテナ間・NAT 後の宛先を網羅すること |

**B は rebinding にも効く**（接続先アドレスで判定するため）。
**VPC のルート設計だけでは不十分**: host/bridge 経路は残り、AWS のリンクローカルは SG/NACL を迂回する。

**ローカルで実測**: Colima の Docker では `FORWARD`（policy `DROP`）の**先頭が `DOCKER-USER`** で中身は空。
ここに egress 規則を置けば、コンテナの転送トラフィック全部に効く。
**ただし host 宛て（bridge → ホスト自身）は `FORWARD` を通らないので別途 `INPUT` 側で扱う。**

### 7.3 A を選ぶ場合の要件（旧 FR-1/FR-2 を置き換え）

- **FR-A1 宛先ポリシー**: 範囲リストではなく**ポリシー**として定義する。
  IANA special-purpose レジストリ（IPv4/IPv6）を分類の入力とし、**明示的な例外**を文書化する。
  最低限: `127.0.0.0/8`、RFC1918、`169.254.0.0/16`、`fe80::/10`、`fc00::/7`、`::1`、
  `0.0.0.0/8`・`::`、**`::ffff:0:0/96`（バイナリ正規化して埋め込み IPv4 を分類）**、
  `224.0.0.0/4`・IPv6 multicast、`240.0.0.0/4`。
  **`100.64.0.0/10`・`198.18.0.0/15`・`192.0.0.0/24`・`fec0::/10` は環境依存のポリシー選択**として明記。
  **`64:ff9b::/96`（NAT64）は内部とは限らない**——翻訳を考慮しないなら拒否側に倒す理由を書く。
  **「公開 IP ＝ 安全」ではない**: 展開固有の保護対象（グローバル IP を持つ内部サービス）も対象。
- **FR-A2「いずれか」規則を維持**: 解決結果の**1 つでも**禁止なら拒否。「全部」にすると、
  接続側に全アドレスが渡る限り安全でない。混在 DNS の Provider は**意図的に失敗**させる。
  （代替: 禁止アドレスを捨てて許可分だけに固定する——**別の要件**として扱う）
- **FR-A3 接続の不変条件**: 固定は**全接続・全フォールバック**に効き、
  元の `Host` ヘッダと TLS のホスト名検証を**保つ**。A/AAAA 両方を対象、空・エラー結果は失敗、
  **未検査の DNS フォールバックなし**。リテラル IP も同じポリシーを通す。
- **FR-A4「接続前」**: 旧 FR-1c の「ネットワーク要求の前」は**「上流への接続前」**と読む。
  DNS 解決自体はネットワークを使う。
- **FR-A5 依存**: アドレス分類は transport 非依存。**接続固定の実装が `undici` を要するなら足してよい**
  （旧 FR-1e の「足さない」を撤回。FR-2b との矛盾を解消）。
- **FR-A6 対象経路**: 「6 箇所」ではなく**上流へ出る全要求経路**（`mppx.rawFetch` を含む 10 経路と、
  将来増えるもの）。**チョークポイント**（`urlFor` / `${base}${path}`）で止めることを設計で確認する。

### 7.4 共通要件（A・B どちらでも）

- **FR-C1 診断の分類**: 生のアドレスを出さない代わりに、**固定カテゴリ**を定める:
  `destination_blocked` / `dns_failed` / `connect_failed` / `upstream_timeout`。
  公開応答は汎用失敗、**運用者向けログはカテゴリ + routeId + ポリシー版**。
  生アドレスを残すなら**アクセス/保持ポリシー**を明記する。
- **FR-C2 fixture 例外**: `synthetic` と non-signing fixture は loopback を要する（`config.ts:99`）。
  A なら `real` モードに限定、B なら試験環境に規則を適用しない。**どちらも文書化**。

### 7.5 §5「価格」の書き直し

旧 §5 は実装コストを列挙し、利点を「再起動を省ける」に矮小化していた——**一方に寄っていた**。
正しくは: **機能の価値（動的な Provider 発見・要求ごとの選択）は未確定**であり、
その確定が先。**B（インフラ側）は運用コストで、A（アプリ側）は実装コストで**、どちらにも価格がある。

### 8.2 B（インフラ側）の前提条件（指摘3）

B を選ぶなら、**展開先の実態を先に確認**する。`DOCKER-USER` の有無は backend に依存する:

| 項目 | 事実 |
|---|---|
| iptables backend | `DOCKER-USER` は Linux の**転送**トラフィックに効く。**host 宛ては `INPUT`** で別に扱う。**コンテナ自身の loopback** は対象外。同一 bridge 内のフィルタは bridge/netfilter 設定に依存 |
| **nftables backend** | **`DOCKER-USER` は存在しない**。別テーブルを適切な hook/priority で置く |
| IPv6 | iptables backend は `ip6tables` 有効時に IPv6 `DOCKER-USER` を作る（通常は既定）。ただし**コンテナの IPv6 転送自体は既定で無効** |

**展開受け入れ不変条件（B を採る場合に必須）**:
> **実際の Router の network namespace から、禁止宛先に接続試行パケットが 0 個**であること。
> 有効な全アドレスファミリ、loopback、host、隣接コンテナ、ルート経由・変換後の宛先、
> DNS rebinding、proxy 迂回の各試行について、**強制側のカウンタか宛先側の観測**で確認する。
> 許可された DNS と上流への接続性、**再起動後の永続**も確認する。
> **`curl` が失敗することだけでは証拠にならない。**

### 8.3 A（アプリ側）の transport 要件（指摘5）

**チョークポイントで URL を検査しても、接続は固定されない。** `urlFor` / `${base}${path}` が
検査済み URL **文字列**を返しても、transport が独自に名前解決すれば rebinding に負ける。

→ **FR-A7**: 検査済みアドレスで接続する transport が、**全 fetch**（SDK 経由の `mppx.rawFetch`、
後段の有料要求を含む）に**到達している**ことを要件にする。URL 検査と接続固定は**別の層**である。

`rawFetch` は `urlFor` を**迂回しない**（3 箇所すべてが `urlFor` の結果を使う。自分で確認）。
経路数は **10**: MPP 3、実 x402 3（`getChallenge` の呼び出し元 2 を含む）、合成 x402 2、受信 2。
§7.1 の内訳（9）は誤りだった。

### 8.4 診断と fixture 例外の確定（指摘6）

**FR-C1'**: 分類は**証拠に基づく**。B では**firewall の drop はタイムアウトに見える**ので、
強制側のテレメトリ無しに `destination_blocked` を**報告してはならない**。
**不確定な transport 失敗**（`transport_failed`）を許し、**経過時間から遮断を推定しない**。

**FR-C2'**: 「A は `real` モードに限定」では **non-signing fixture を除外できない**
（それらは**実 adapter モードで動く**）。例外は**明示的な fixture 能力/エンドポイント**に限定し、
**本番の強制は常に有効**。

### 8.5 レビューが「変更不要」と確認したもの

- FR-A2「いずれか拒否」は安全で意図的に保守的。固定があれば INV-1 より厳しいが、可用性の代償は受容可
- §7.5 の価格の書き方は owner の判断材料として均衡している

## 9. INV-1' の強制点の分担（B の設計レビューを受けた改訂）

2026-10-01。B の設計（`ssrf-egress-design.md` §8）が REJECT され、うち 1 件は規則の誤りではなく
**手段の構造的限界**だった: コンテナ内 loopback・自アドレス宛ての接続は network namespace を出ないため、
host 側の規則は**定義上**見られない（実測 10、13）。レビューは「要件の明示的な改訂」か「namespace 内を
カバーする強制点」のどちらかを求めた。**要件を改訂する**。設計レビュー #2（同 §10）の指摘 3・6 を反映済み。

**INV-1''（§8.1 の INV-1' を分担として書き直す）**:

| 宛先 | 強制点 | 不変条件 |
|---|---|---|
| Router の namespace を**出る**宛先（host の全アドレス、隣接コンテナ、VPC、link-local、変換後の宛先、rebinding 先） | **B**（host 側 egress 規則） | **禁止宛先に届く接続試行パケットが 0**（host の socket 層に受理されない、上流へ出ない）。B はパケットが namespace を出た後に見るので、「出ない」ではなく「届かない」が正しい |
| namespace を**出ない**宛先（`127.0.0.0/8`、`::1`、コンテナ自身のアドレス、`127.0.0.11`） | **A**（fetch 前の分類 + 接続固定） | host からは見えない。`HEALTHCHECK` と既定 listen が loopback を正当に使うので、「全部塞ぐ」は不可 |

- **INV-1' の完成は B + A**。B 単独の完了を INV-1' の完了と**呼ばない**
- **release gate**: 「AI が上流 URL を指定する」機能は、**B と A の両方の受け入れが通るまで出さない**
- A の範囲は当面 **namespace 内の宛先の拒否と、解決済みアドレスへの接続固定**に絞れる。
  範囲一覧の網羅は B が担う（A にも同じ分類を入れてよいが、要件ではない）
- B は Router を**専用の user-defined bridge に単独で**置く（§2 の「既定 bridge」の事実は設計で変わる）。
  理由: 同一 bridge の隣接は `br_netfilter` 無しでは規則で止められない（実測 16）
- **DNS**: §8.1 の例外「承認済みリゾルバへの DNS トラフィックのみ」は、**port 番号による例外規則では実装できない**
  （同じ宛先の 53 番への HTTP を通してしまう）。B の規則集に DNS 例外を**置かない**。
  代わりに、Docker の埋め込み resolver の上流を **host の loopback resolver** にすることを展開条件とし、
  上流問い合わせが host の namespace から出ることを**検証で確認**する（設計 §11.3。実測 25・31 で両方向を確認）。
  上流が非 loopback の構成では問い合わせがコンテナ namespace から出て規則に落ちるので、
  正しい対処は loopback resolver の導入であって例外の追加ではない

この改訂で §8.6 の「B を選ぶ: コード変更なし」は **「B は手順書と検証、A は後続の設計」**に変わる。
着手条件（「AI が上流 URL を指定する」判断とセット）は変わらない。
