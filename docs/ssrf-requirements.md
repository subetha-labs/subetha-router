# 要件: SSRF 防御（段階 0 / 1 / 2）

> 2026-10-01。`generalization-requirements.md` §15.2 の FR-8''' が「警告のみ」と縮小したのは、
> **上流 URL が設定値であり攻撃者が注入できない**ためだった。
> owner が「AI が上流 URL を指定する」方向を検討しているため、その前提が崩れる場合に
> 何が必要かを**段階ごとに**定める。段階 0 はコード変更なし。

## 1. 脅威の定義（何を守るか）

SSRF は「**Router の立場で任意の URL へ到達させる**」攻撃である。被害は**到達そのもの**であり、
支払いでも応答本文でもない。したがって次の 2 つでは**防げない**（実測で確認済み）:

| 案 | 守れるもの | 守れないもの |
|---|---|---|
| 402 を確認した先にしか払わない | 誤った支払い | 到達は fetch 時点で起きている |
| 上流の本文・例外文字列を返さない | 本文の漏洩 | **応答時間**（0ms / 15ms / 5000ms が区別できる）と **GET の副作用** |

両方とも**既に実装済み**（`redirect: "error"`、`SAFE_REASONS` 許可リスト）。
残るのは**fetch の前に止める**層だけである。

## 2. 事実（デプロイ先と実装の現状）

| 事実 | 出所 |
|---|---|
| コンテナは既定 bridge ネットワーク（`--network` 指定なし） | `DEPLOY.md:46` |
| IMDSv2 の強制は**ドキュメントに記載なし**（= AWS 既定の v1 許可が残り得る） | `DEPLOY.md` 全体 |
| Router 自身は IMDS を**使わない** | `grep` で参照 0 件 |
| 上流への `fetch` は **6 箇所**（素の `globalThis.fetch`、`undici` 非依存） | 実測 |
| quote の失敗は即返り、**レート制限なし** | `orchestrator.ts:305,317,379` |
| 合成 fixture は **loopback を要する** | `config.ts:99` |

## 3. 4 層の防御と、各層が止める攻撃

| # | 防御 | 止める攻撃 | 状態 |
|---|---|---|---|
| 1 | fetch 前のアドレス範囲検査（**DNS 解決後**） | 内部アドレスの直接指定、`evil.com → 10.0.0.5` の解決 | **未実装** |
| 2 | 接続時のアドレス固定 | DNS rebinding（検査と接続の間に答えを変える） | **未実装**（`undici` 依存が要る） |
| 3 | リダイレクト禁止 | 302 で内部へ飛ばす | 実装済み |
| 4 | 本文・例外文字列を出さない | 到達後の内容漏洩 | 実装済み |

**#1 だけでは #2 の攻撃に負ける。** ただし #1 が直接指定の攻撃を全て止め、
#2 が守るのは攻撃者が自前 DNS を持つ場合に限られる。優先順位は #1 > #2。

## 4. 段階と要件

### 段階 0: インフラで IMDS 経路を塞ぐ（コード変更なし・**今やる**）

**FR-0a**: `DEPLOY.md` に IMDSv2 の強制を追記する。
`HttpTokens=required` に加え **`HttpPutResponseHopLimit=1`** とする。

理由: hop limit 1 なら、**コンテナ（ホストから 1 hop 先）からメタデータに届かない**。
Router は IMDS を使わない（§2）ので、塞いでも Router は困らない。
これで **最も危険な標的（IAM 認証情報）が #1 の実装前に消える**。

**FR-0b**: §9 の「EC2 側で必要なこと」に置く。既存の記述（SG・TLS・鍵）と同列の
**範囲外事項**であり、Router の挙動を変えない。

**受け入れ条件**: AC-0 — 手順が `aws ec2 modify-instance-metadata-options` の
具体的なコマンドとして書かれ、**確認コマンド**（現在値の読み出し）を伴う。

### 段階 1: fetch 前のアドレス検査（**「AI が URL を指定する」機能を採用する時点で必須**）

**FR-1a**: `real` モードの上流 fetch（6 箇所）に限り、**fetch 直前に hostname を DNS 解決**し、
返った**全アドレス**を検査する。1 つでも次に該当すれば **fetch しない**:
loopback、private（10/8, 172.16/12, 192.168/16）、link-local（169.254/16, fe80::/10）、
ULA（fc00::/7）、IPv4-mapped IPv6、`::1`、unspecified（0.0.0.0, ::）。

**FR-1b**: `synthetic` モードは対象外（fixture が loopback を要する）。

**FR-1c**: 拒否は**ネットワーク要求の前**であること。拒否の理由は固定コードで、
解決したアドレスを応答・journal・ログに**出さない**。

**FR-1d**: **DNS rebinding は防げない**ことを明記する（受容ではなく段階 2 の課題）。

**FR-1e**: `undici` を依存に**足さない**。既存の `fetch` 呼び出しの前段に同じ検査を置く。

### 段階 2: 接続時のアドレス固定（**段階 1 と同じ PR で入れる**）

**FR-2a**: `undici` を依存に追加し、解決済みアドレスへの接続を `dispatcher` で強制する。
検査したアドレス以外に接続しない。

**FR-2b**: 段階 1 と**分けない**。分けると「機能だけ先に出て rebinding に開いた期間」ができる。

## 5. 段階 1・2 に進む条件（判断は owner）

「AI が上流 URL を指定する」機能を採用する判断と**セット**で着手する。
採用しないなら段階 0 だけで脅威自体が存在しない。

採用の価格: 段階 1 + 2 + `undici` 依存 + 6 箇所の配線 + fixture との分離。
得られるもの: 設定への追記と再起動を省ける。

段階 1・2 の着手時期。`undici` の版。検査を adapter ごとに置くか共通関数にするか（設計で決める）。
