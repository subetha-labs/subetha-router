# 要件: 宛先の認可 — 汎用 Router 化の第一歩

> 2026-09-30。`docs/price-risk-findings.md` §4 で「汎用化の障害は価格ではなく宛先の認可」と
> 確定したことを受けた設計。**価格リスク・レート換算は対象外**（mainnet 対応時の課題）。

## 1. 現状（ソースで確認した事実）

### 1.1 `routeId` が兼ねている役割

| # | 役割 | 実装 |
|---|---|---|
| 1 | **上流 URL の解決** | `upstreams[routeId]`（設定。未知は解決不能） |
| 2 | **route の存在検査** | `orchestrator.ts:285` が未知を `unknown_route` で拒否 |
| 3 | **予算の入口** | 設定に無い route は quote できない |
| 4 | **承認の対象** | subject に `resource.url`（= Router 自身の canonical URL） |
| 5 | **`routeBinding`** | `routeId\|GET\|canonicalPath`（`config.ts:85`） |

### 1.2 **重要: 上流 URL は承認対象にも束縛にも入っていない**

- `routeBinding` = `routeId|GET|canonicalPath`。**`canonicalPath` は Router 自身のパス**
  （`/v1/routes/{routeId}/resource`）であり、**上流 URL を含まない**
- `routeListBody`（`projection.ts:14`）のコメントに明記: **「上流 URL は返さない」**（意図的な秘匿）
- 承認 subject（`tools.ts:164-167`）の destination は **`quoted` / `asset` / `network` のみ**。
  **`payTo` も上流 URL も含まれない**

**したがって現在、人間は「どこに払うか」を承認していない。**
それは設定時に運用者が決めているため、承認の時点では不要だった。

**ここが汎用化で最も重要な変更点**である: 宛先が動的になるなら、
**承認対象に宛先を含めなければ、人間は何を承認しているのか分からなくなる**。

### 1.3 価格は既に動的（変更不要）

上流の価格・資産・宛先は 402 を読んで取得している（`x402.ts:84-102`）。
固定されているのは **URL と route 定義だけ**。
→ 汎用化に必要なのは「任意 URL の受け入れ」であり、「価格調査の追加」ではない。

## 2. 目的とスコープ

**目的**: AI が「使いたい Provider の URL」を Router に渡し、
設定に事前登録されていない宛先に対しても購入を成立させる。

**このスライスで満たすこと**
- 任意の上流 URL を受け付ける経路を作る
- **宛先を認可する仕組み**を、設定への事前登録以外の形で用意する
- 宛先が動的になったことを**承認の対象に反映**する

**このスライスで満たさないこと**
- 価格リスク・レート換算・手数料（`price-risk-findings.md` §2.4）
- Provider の選定・比較（それは Router の役割ではない）
- 異資産間の変換（同一資産のプロトコル変換で汎用 Router は成立する）

## 3. 認可方式の候補

| 方式 | 宛先を認可するもの | 長所 | 短所 |
|---|---|---|---|
| **A. オリジン allowlist** | 運用者が設定したオリジン（`https://*.example.com`） | 承認の意味が保たれる。変更が中規模 | 「世の中の Provider」には届かない |
| **B. 宛先ごとの人間承認** | 人間が quote ごとに宛先を見て承認 | 最も汎用。Router は判断しない | 承認回数が宛先数に比例。予算だけでは守れない |
| **C. 承認済み宛先の学習** | 初回は人間、以降は予算内で自動 | 現実的 | **新しい永続信頼ストア**が必要。「後で悪意を持つ宛先」への対処が要る |

### 3.1 採るべき順序

**A → B を同時に満たす形を提案する**（C は次スライス）。

理由: A と B は排他ではなく**階層**である。
- allowlist に**載っている**オリジン → 従来通り（宛先は運用者が保証済み）
- allowlist に**載っていない**オリジン → **拒否**（本スライス）または
  **宛先を承認対象に含めたうえで人間承認**（B、将来）

つまり本スライスでは **A を実装し、B のための土台（承認 subject への宛先追加）を同時に作る**。
B の「未登録オリジンを人間承認で通す」部分は、A が動いてから別途判断する。

## 4. 要件

- **FR-1 動的 URL の入口**: quote 要求に上流 URL を渡せる経路を設ける。
  既存の `routeId` 指定は**そのまま動く**（後方互換）。
- **FR-2 オリジン allowlist**: 設定に許可オリジンの一覧を持つ。
  **allowlist に無いオリジンは quote を成立させない**（fail closed）。
  ワイルドカードを許すなら、その範囲を明示的に定義する。
- **FR-3 宛先を承認対象に含める**: 動的 URL 経路では、承認 subject に
  **上流のオリジンと `payTo`** を含める。人間が「どこに払うか」を見られるようにする。
  **既存の静的 route の subject は変えない**（後方互換／chat 契約）。
- **FR-4 予算は宛先に依存しない**: 予算バケットは `(network, asset)` のままとし、
  **オリジン単位の予算は本スライスでは導入しない**。
  ただし「予算内なら任意の宛先に払える」状態を作らないため、FR-2 が必須。
- **FR-5 `routeBinding` の一意性を保つ**: 動的 URL の購入も
  「承認した経路以外で使い回せない」性質を保つ。上流 URL が異なれば
  **異なる束縛**になること。
- **FR-6 上流 URL を漏らさない**: `routeListBody` の既存方針（上流 URL を返さない）を
  維持する。ただし FR-3 で**承認者には**オリジンを見せる。
  「一覧では出さないが、承認時には示す」を区別する。
- **FR-7 core を触る範囲を明示する**: `unknown_route`（`orchestrator.ts:285`）の
  緩和が必要になる。**どこまで core を変えるかを設計時に確定**し、
  レール非依存性を壊さないこと。

## 5. 未解決（設計フェーズで詰める）

- **U-1**: 動的 URL をどう渡すか（quote 引数の新フィールド？ 別ツール？）
- **U-2**: `routeId` が無い購入で `routeBinding` をどう作るか
  （URL のハッシュ？ 正規化したオリジン+パス？ 正規化規則が攻撃面になる）
- **U-3**: allowlist のワイルドカード構文と、その照合規則
  （サブドメイン乗っ取り・IDN・ポート・スキームの扱い）
- **U-4**: 上流が返す `payTo` は上流が自由に決められる。
  **オリジンを認可しても `payTo` は認可していない**。これを許容するか、
  `payTo` も allowlist するか
- **U-5**: SSRF。任意 URL を Router が fetch するので、
  **内部ネットワーク・メタデータエンドポイントへのアクセスを防ぐ**必要がある
  （`127.0.0.1` / `169.254.169.254` / `.internal` 等）。これは必須要件に昇格すべき可能性

## 6. 受け入れ条件（暫定）

| ID | 条件 |
|---|---|
| AC-1 | allowlist に載ったオリジンの任意パスで quote が成立する |
| AC-2 | **allowlist に無いオリジンは quote が成立しない** |
| AC-3 | 動的 URL の承認 subject に**オリジンと `payTo`** が含まれる |
| AC-4 | 既存の静的 route の挙動と subject が**変わらない**（回帰） |
| AC-5 | 上流 URL が異なれば `routeBinding` が異なる |
| AC-6 | `routeListBody` が上流 URL を漏らさない（既存性質の維持） |
| AC-7 | **ループバック・プライベート IP・メタデータ URL への fetch を拒否する**（U-5） |

## 7. 本書で決めていないこと

実装の着手、U-1〜U-5 の結論、C（学習型）の採否。
**U-5（SSRF）は設計フェーズで必須要件に昇格する可能性が高い**と考えている。

## 8. 独立レビュー結果: **2 件の blocker** — 要件を全面改訂する

レビュー実施: 2026-09-30、`gpt-6-astra`、`--sandbox read-only`。
**blocker 2 件**（SSRF、起動時 route 解決）と設計不備 5 件。実ソースで再確認して改訂する。

### 8.1 私の事実誤認（最も重要）

**「人間は『どこに払うか』を承認していない」（§1.2）は言い過ぎだった。**

`src/config.ts:21-25` の型名は **`DestinationAllow`**（宛先の許可）であり、
`scheme` / `network` / `asset` / **`payTo`** を持つ。
`selectOffer`（`orchestrator.ts:184-190`）は**この 4 つすべての一致を要求**する。

つまり**現状は運用者が設定で受取先を明示的に認可している**。
承認 subject に `payTo` が出ないのは事実だが、それは
「誰も認可していない」ではなく「**設定時に認可済みだから承認時に不要**」だった。

→ **オリジン allowlist への移行は「認可の追加」ではなく「既存の受取先制約の除去」を含む。**
これは要件の性質を変える。単に URL を動的にする話ではない。

### 8.2 Blocker 1: SSRF は要件（U-5 → FR に昇格）

FR-2 は「quote を成立させない」だけで、**ネットワーク要求を止めていない**。
challenge 取得・再照合・有料要求のいずれもが AI 指定の URL を fetch する。
**拒否が事後なら SSRF は成立してしまう。**

現状の防御（実測）:
- `redirect: "error"` と timeout は**両 adapter にある**
  （`x402.ts:252,282,462` / `mpp.ts:200,305,370,429`）→ リダイレクト経由の内部到達は防げている
- しかし URL 検証は **http(s) とクエリ有無のみ**（`config.ts:376-390`）。
  **アドレス範囲・DNS rebinding・接続時検証は無い**

→ **FR-8（新規・必須）**: 認可は**あらゆるネットワーク要求の前**に行う。
URL パース後かつ **DNS 解決後**に禁止宛先を拒否し、**接続時に強制**する
（検証と fetch の間の race を避ける）。対象は IPv4/IPv6、IPv4-mapped、
10 進/8 進/16 進表記、loopback・private・link-local、内部 DNS 名、メタデータ endpoint。
**ホスト名 allowlist だけでは、許可ホストが内部アドレスに解決する場合を防げない。**
リダイレクトは無効のまま維持する。**AC-7 を必須にする。**

### 8.3 Blocker 2: `unknown_route` の緩和だけでは動かない

`src/main.ts:103-145` が起動時に route を列挙して
`routeBinding → inbound adapter` の逆引きを作り、**未知の束縛は fail closed**。
さらに x402/MPP 受信は `<rail>:<routeId>` で選ばれる。

静的前提はここだけではない（レビューが列挙）:

| 箇所 | 前提 |
|---|---|
| `main.ts:70-90` | 送信レールも起動時 route map から選ぶ |
| `x402.ts:255` / `mpp.ts:203` | 上流 URL が起動時 map にある |
| `app.ts:276,286,313` | quote・purchase が設定済み route を要求 |
| `projection.ts:37` | quote 投影が `RouteConfig` を要求 |
| `client/index.ts:240,295` | quote が `routeId`、実行が固定 resource path を期待 |
| `mcp/tools.ts:180` / `server.ts:173` | ツール I/F が `routeId` 必須 |
| chat 契約テスト | 固定 route / 固定 upstream を前提 |

→ **FR-9（新規）**: 動的購入には**不変の purchase descriptor** を設ける。
両レールと宛先をライフサイクル全体で解決でき、**再起動後も保持**される。
**決して credential などの非信頼入力から adapter を選ばない。**

なお**予算の再構築は blocker ではない**: `budget.ts:61-83` は journal の予約額から
直接復元し、route を参照しない。ただし `Intent` に上流 URL やレール選択の
記述子が無い（`intent.ts:98`）ため、予算が保たれても動的経路は復元できない。

### 8.4 オリジン認可は受取先認可ではない（U-4 の結論）

allowlist に載った**悪意ある**オリジンは、攻撃者の `payTo` と
予算内の額を最初から提示できる。承認・受信支払いを経て
**代金を受け取りながら無価値なデータを返す**ことが可能。

既存の完全一致照合（`orchestrator.ts:669` / `x402.ts:353` / `mpp.ts:379`）は
**承認後の差し替え**を防ぐが、**最初に提示された受取先の信頼性は保証しない**。

さらに: 正規のオリジンでも、**パスによって別のテナント/受取人が応答する**構成なら、
AI は攻撃者のテナントを選べる。**オリジンだけを表示すると、この区別が隠れる。**

→ **FR-3 改訂**: 表示を足すだけでは不十分。
**実際に実行される不変 offer に表示情報を束縛する**。
方式は次のいずれかを明示的に選ぶ:
(a) 運用者が「受取先選択権をオリジンに委譲する」と設定で宣言する、
(b) **quote された受取先とリソースそのものを人間が承認する**。

### 8.5 FR-5 / U-2: 正規化を避ける

危険なのは「**異なる 2 つの実効要求が同じ承認を共有する**」ことと
「承認後に束縛が再解釈される」こと。URL 正規化の攻撃面は広い
（スキーム/ホストの大小、既定ポート、IDN、末尾ドット、パスの大小・末尾スラッシュ・
dot segment・エンコード区切り・多重デコード、クエリ順・重複・空値、userinfo、fragment）。

→ **FR-5 改訂**: **URL 正規化で束縛の同一性を決めない。**
サーバ生成の**不透明な識別子**を、検証済み fetch URL・method・レール・承認条件を含む
**不変記述子**に割り当てる。credential はその識別子に束縛し、
**常に保存された記述子を実行する**。purchase 時の入力から再構築しない。
URL パースと SSRF 検証は別途必要。

`userinfo` と `fragment` は**曖昧に扱わず拒否**する。
現状 adapter はクエリを拒否している（`config.ts:376` の `allowQuery=false`）。
**この制約を維持するか、サポートを定義する**かを明示する
（「オリジン + パス」ではクエリで選ばれるリソースを表現できない）。

→ さらに: **同一 `requestId` で宛先が違えば衝突させる**。
現状は `routeId` しか比較していない（`orchestrator.ts:288-298`）。

### 8.6 FR-4（予算）: 判断は妥当だが理由が不完全

`(network, asset)` バケット維持は**誤りではない**。
ただし「FR-2 だけで意図しない受取先への支払いを防げる」という含意は誤り
（§8.4 の受取先方針に依存する）。

悪意あるオリジン 1 つが**共有予算を食い潰し**、他 Provider の枠を奪える。
オリジン単位の予算を後回しにするなら、**この共有予算の露出を明示的に受け入れる**と書く。

### 8.7 FR-7 の抜け: 受信側の条件（source terms）の権威が未定義

現状 `source.amount` / `asset` / `network` は**設定の route 由来**
（`orchestrator.ts:308-324`）で、上流の額とは独立。
route 登録を外すと、**これらを誰が決めるのかが未定義**になる。
受信レール選択も同様。

→ **FR-10（新規）**: 動的購入用の**支払いプロファイル**（受信条件の権威）を設定で定義する。
価格・FX・手数料を持ち込まずに定義できる。

### 8.8 私が独自に見つけた点（レビューと整合）

受信レールの**非対称性**:
- **SubEtha は route 非依存のインスタンス 1 個**（facilitator が challenge で `payTo` を返す）
- **x402 / MPP は route ごと**（Router が payee で `payTo` を設定から持つ）

→ **動的化は送信側に限定すれば範囲が大幅に縮む。**
owner の構想（「AI が使いたい Provider を選ぶ」）は**送信側の話**であり、
**受信側を動的にする必要はない**。§8.3 の blocker の多くは受信側に起因する。

### 8.9 改訂の方向（次フェーズで設計する）

1. **スコープを送信側に限定**する（受信は既存の設定 route のまま）
2. **不変 purchase descriptor**（FR-9）＋ **不透明識別子による束縛**（FR-5 改訂）
3. **SSRF を必須要件に**（FR-8）
4. **受取先の認可方式を明示的に選ぶ**（FR-3 改訂の (a) か (b)）
5. **受信条件の権威を定義**（FR-10）
6. 共有予算の露出を明示的に受け入れる（FR-4）
