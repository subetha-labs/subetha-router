# 要件: 宛先の認可 — 汎用 Router 化の第一歩

> 2026-09-30。`docs/price-risk-findings.md` §4 で「汎用化の障害は価格ではなく宛先の認可」と
> 確定したことを受けた設計。**価格リスク・レート換算は対象外**（mainnet 対応時の課題）。

## 1. 現状（ソースで確認した事実）

### 1.1 `routeId` が兼ねている役割

| # | 役割 | 実装 |
|---|---|---|
| 1 | **上流 URL の解決** | `upstreams[routeId]`（設定。未知は解決不能） |
| 2 | **route の存在検査** | `orchestrator.ts:285` が未知を `unknown_route` で拒否 |
| 3 | **予算の入口** | 設定に無い route は quote できない |
| 4 | **承認の対象** | subject に `resource.url`（= Router 自身の canonical URL） |
| 5 | **`routeBinding`** | `routeId\|GET\|canonicalPath`（`config.ts:85`） |

### 1.2 **重要: 上流 URL は承認対象にも束縛にも入っていない**

- `routeBinding` = `routeId|GET|canonicalPath`。**`canonicalPath` は Router 自身のパス**
  （`/v1/routes/{routeId}/resource`）であり、**上流 URL を含まない**
- `routeListBody`（`projection.ts:14`）のコメントに明記: **「上流 URL は返さない」**（意図的な秘匿）
- 承認 subject（`tools.ts:164-167`）の destination は **`quoted` / `asset` / `network` のみ**。
  **`payTo` も上流 URL も含まれない**

**したがって現在、人間は「どこに払うか」を承認していない。**
それは設定時に運用者が決めているため、承認の時点では不要だった。

**ここが汎用化で最も重要な変更点**である: 宛先が動的になるなら、
**承認対象に宛先を含めなければ、人間は何を承認しているのか分からなくなる**。

### 1.3 価格は既に動的（変更不要）

上流の価格・資産・宛先は 402 を読んで取得している（`x402.ts:84-102`）。
固定されているのは **URL と route 定義だけ**。
→ 汎用化に必要なのは「任意 URL の受け入れ」であり、「価格調査の追加」ではない。

## 2. 目的とスコープ

**目的**: AI が「使いたい Provider の URL」を Router に渡し、
設定に事前登録されていない宛先に対しても購入を成立させる。

**このスライスで満たすこと**
- 任意の上流 URL を受け付ける経路を作る
- **宛先を認可する仕組み**を、設定への事前登録以外の形で用意する
- 宛先が動的になったことを**承認の対象に反映**する

**このスライスで満たさないこと**
- 価格リスク・レート換算・手数料（`price-risk-findings.md` §2.4）
- Provider の選定・比較（それは Router の役割ではない）
- 異資産間の変換（同一資産のプロトコル変換で汎用 Router は成立する）

## 3. 認可方式の候補

| 方式 | 宛先を認可するもの | 長所 | 短所 |
|---|---|---|---|
| **A. オリジン allowlist** | 運用者が設定したオリジン（`https://*.example.com`） | 承認の意味が保たれる。変更が中規模 | 「世の中の Provider」には届かない |
| **B. 宛先ごとの人間承認** | 人間が quote ごとに宛先を見て承認 | 最も汎用。Router は判断しない | 承認回数が宛先数に比例。予算だけでは守れない |
| **C. 承認済み宛先の学習** | 初回は人間、以降は予算内で自動 | 現実的 | **新しい永続信頼ストア**が必要。「後で悪意を持つ宛先」への対処が要る |

### 3.1 採るべき順序

**A → B を同時に満たす形を提案する**（C は次スライス）。

理由: A と B は排他ではなく**階層**である。
- allowlist に**載っている**オリジン → 従来通り（宛先は運用者が保証済み）
- allowlist に**載っていない**オリジン → **拒否**（本スライス）または
  **宛先を承認対象に含めたうえで人間承認**（B、将来）

つまり本スライスでは **A を実装し、B のための土台（承認 subject への宛先追加）を同時に作る**。
B の「未登録オリジンを人間承認で通す」部分は、A が動いてから別途判断する。

## 4. 要件

- **FR-1 動的 URL の入口**: quote 要求に上流 URL を渡せる経路を設ける。
  既存の `routeId` 指定は**そのまま動く**（後方互換）。
- **FR-2 オリジン allowlist**: 設定に許可オリジンの一覧を持つ。
  **allowlist に無いオリジンは quote を成立させない**（fail closed）。
  ワイルドカードを許すなら、その範囲を明示的に定義する。
- **FR-3 宛先を承認対象に含める**: 動的 URL 経路では、承認 subject に
  **上流のオリジンと `payTo`** を含める。人間が「どこに払うか」を見られるようにする。
  **既存の静的 route の subject は変えない**（後方互換／chat 契約）。
- **FR-4 予算は宛先に依存しない**: 予算バケットは `(network, asset)` のままとし、
  **オリジン単位の予算は本スライスでは導入しない**。
  ただし「予算内なら任意の宛先に払える」状態を作らないため、FR-2 が必須。
- **FR-5 `routeBinding` の一意性を保つ**: 動的 URL の購入も
  「承認した経路以外で使い回せない」性質を保つ。上流 URL が異なれば
  **異なる束縛**になること。
- **FR-6 上流 URL を漏らさない**: `routeListBody` の既存方針（上流 URL を返さない）を
  維持する。ただし FR-3 で**承認者には**オリジンを見せる。
  「一覧では出さないが、承認時には示す」を区別する。
- **FR-7 core を触る範囲を明示する**: `unknown_route`（`orchestrator.ts:285`）の
  緩和が必要になる。**どこまで core を変えるかを設計時に確定**し、
  レール非依存性を壊さないこと。

## 5. 未解決（設計フェーズで詰める）

- **U-1**: 動的 URL をどう渡すか（quote 引数の新フィールド？ 別ツール？）
- **U-2**: `routeId` が無い購入で `routeBinding` をどう作るか
  （URL のハッシュ？ 正規化したオリジン+パス？ 正規化規則が攻撃面になる）
- **U-3**: allowlist のワイルドカード構文と、その照合規則
  （サブドメイン乗っ取り・IDN・ポート・スキームの扱い）
- **U-4**: 上流が返す `payTo` は上流が自由に決められる。
  **オリジンを認可しても `payTo` は認可していない**。これを許容するか、
  `payTo` も allowlist するか
- **U-5**: SSRF。任意 URL を Router が fetch するので、
  **内部ネットワーク・メタデータエンドポイントへのアクセスを防ぐ**必要がある
  （`127.0.0.1` / `169.254.169.254` / `.internal` 等）。これは必須要件に昇格すべき可能性

## 6. 受け入れ条件（暫定）

| ID | 条件 |
|---|---|
| AC-1 | allowlist に載ったオリジンの任意パスで quote が成立する |
| AC-2 | **allowlist に無いオリジンは quote が成立しない** |
| AC-3 | 動的 URL の承認 subject に**オリジンと `payTo`** が含まれる |
| AC-4 | 既存の静的 route の挙動と subject が**変わらない**（回帰） |
| AC-5 | 上流 URL が異なれば `routeBinding` が異なる |
| AC-6 | `routeListBody` が上流 URL を漏らさない（既存性質の維持） |
| AC-7 | **ループバック・プライベート IP・メタデータ URL への fetch を拒否する**（U-5） |

## 7. 本書で決めていないこと

実装の着手、U-1〜U-5 の結論、C（学習型）の採否。
**U-5（SSRF）は設計フェーズで必須要件に昇格する可能性が高い**と考えている。
