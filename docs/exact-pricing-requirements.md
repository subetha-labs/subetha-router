## 1. 背景

- 今の zUSDC の route は、受け取り 12,000・上流 10,000 の固定（base units、6 桁）。差額 2,000【事実：`tools/remote-mcp-config.ts` の `HOSTED_EXACT`】。
- 2026-11-24 から、買い手の支払いは SubEtha の settle facilitator が送り、gas は SubEtha の運用者が払う【事実】。実費は 1 件 156,633 gas、約 9.4e-7 ETH【事実：本番の 2 件】。
- `/costs` は、直近 n 件の tx の実費（成功した件の中央値・p90）、`overheadRate`（失敗などの割合）、今の `baseFeePerGas` を wei で返す。item は `txHash` を持つが、**注文・呼び出し側の識別は無い**（まとめ送りでは、同じ `txHash` の item が複数の注文・呼び出し側の分で並ぶ）。費用が無い・全件が未完成の時は `overheadRate` が null。認証は settle 先と同じ token【事実】。
- 静的 route の額は、設定の固定値として、offer の照合・指紋・一覧・予算に入っている【事実：`src/core/orchestrator.ts`・`src/config.ts` の `authoritativeTermsOf`】。標準の x402 入口には quote が無く、402 を返す時（注文の作成）に額が決まる【事実】。
- 額の上限は 20,000（署名の道具の上限と同じ）【事実：`SUBETHA_EXACT_MAX_AMOUNT`】。

## 2. 範囲

**含む**：`subetha-exact` の静的 route の受け取り額を、注文ごとに式で決めるコード・設定・試験・文書。hosted は既定で無効（今の固定のまま）。
上流は、**Base Sepolia の USDC（6 桁、zUSDC と 1:1 とみなす）に x402 で払う route だけ**。ほかの資産・桁・network の route に式を設定したら起動しない。
**含まない**：実費の自動の精算と日ごとの損益の会計（D-4）、本番の有効化、動的 URL とほかの rail の価格、ETH の価格の oracle、引き出しの自動化（(c)）、mainnet、署名の道具の上限の変更、再送。

## 3. 式

単位：額は base units（6 桁、1 USD = 1,000,000）。`ethPrice` は「1 ETH あたりの base units」の整数（3,000 USD なら 3,000,000,000）。`factorBps` は 10,000 = 1 倍。
`overheadPpm` は `overheadRate` × 1,000,000 を切り上げた整数 + 1（相手が小数 6 桁で切り捨てているため）。整数だけで計算し、割り算は全て切り上げ（受け取りが不足しない側）。

```
settleWei = max( p90,  156,633 × (baseFeePerGas + tip) + l1 )
settle    = ceil( settleWei × ethPrice × factorBps × 10^6 / ( 10^18 × 10^4 × (10^6 − overheadPpm) ) )
withdraw  = ceil( K / n )
C         = upstream + settle + withdraw + take
amount    = ceil( C × 10,000 / 9,965 )
markup    = amount − upstream
share     = ceil( amount × 35 / 10,000 )          （0.35% 分。amount − share ≥ C）
```

- `p90`：`/costs?n=20`（20 tx）の `summary.allocatedP90Wei`（成功した件だけ）。`l1`：応答の item の `l1Fee` の最大と設定の下限の大きい方。`tip`：設定値。
- `overheadRate` は「失敗などにかかった費用 ÷ 全費用」なので、成功 1 件あたりに直すには `1 − overheadRate` で割る。p90 に掛けた結果は見積もりで、平均の復元ではない。
- 黒字の保証ではない。実費が見積もりを越えた分は、Router と SubEtha の運用者の持ち出しになる。

### 3.1 設定する値

| 値 | 意味・単位 | 範囲（外なら起動しない） | 案 |
|---|---|---|---|
| `ethPrice`、`ethPriceAt` | 1 ETH の base units と、設定した時刻（UTC） | 10^8 以上 10^11 以下の整数。時刻は ISO 8601 の UTC（`Z`）。範囲外・不正の扱いは下 | 値は運用者【要決定】。有効期間 7 日（1〜30 日） |
| `factorBps` | settle の見積もりの倍率 | 10,000〜100,000 | 15,000 |
| `take` | 取り分（1 件の固定額） | 0〜10,000 | 500 |
| `K`、`n` | まとめて引き出す 1 回の費用、まとめる件数 | `K` 0〜1,000,000、`n` 1〜100 | 18,000（testnet の実測 8,931 + 9,049 の切り上げ）、8 |
| `tip`、`l1Floor` | wei/gas、wei | 0〜10^10、0〜10^15 | 1,000,000（相手の設定と同じ）、2,000 |
| `maxSettle` | settle の見積もりの上限 | 1〜10,000 | 8,000 |
| `maxAmount` | 受け取り額の上限 | `upstream` より大きく 20,000 以下 | 20,000 |
| `maxPerDay` | 1 日（UTC）に出せる件数（R7） | 1〜1,000 | 20 |

**ETH の価格と時刻だけは、起動を止めない**：無い、片方だけ、形が違う、範囲外、時刻が今より 5 分を越えて未来、有効期間を過ぎた、のどれでも、起動はして新しい offer だけを断る（5 分以内の未来は時計のずれとして使う）。
ほかの値の範囲外・形の違いは起動を止める（R2）。

**`n` = 8 とする理由**：40 件の実証では 100 件に届かない。8 件より多くまとめた時の費用は測っていない【未確認】。34,060（mainnet の見積もり）は使わない。
【訂正 2026-11-25】`K` の元の実測は 8 件でなく **7 coin**。SubEtha 側の 18 coin の実測は 9,232 + 引き出し 9,245 = 18,477（0.35% 分 45 を除くと 18,432。内訳は逆算）で、`K` = 18,000 を越える。値は変えていない（見直しは `docs/exact-withdrawal-runbook.md` §9）。

**例**（`ethPrice` = 3,000 USD は計算のための仮の値。上の案、上流 10,000、`settleWei` = 939,798,001,041（今の gas で 1 件。p90 がこれ以下の場合）、`overheadRate` 0 とし `overheadPpm` の +1 は無視）：
settle 4,230、withdraw 2,250、take 500、C 16,980、amount **17,040**、markup 7,040、0.35% 分 60。今の 12,000 より高い。`n` = 40 と置けば 15,234 だが、40 件をまとめる費用は未確認。

## 5. 要件

- **R1（対象）** 式の価格は、設定で式を選んだ `subetha-exact` の静的 route だけ。選ばない route は、一覧・指紋・journal・計算が今と同じ。
- **R2（前提）** 式の route があるのに、settle 先の token（PR #214）が無い、`offerCap` が無い、上流が §2 の対象でない、§3.1 の範囲の外、予算の区分の 1 件の上限が `maxAmount` 未満、のどれかなら起動しない（固定文）。
- **R3（読み取り）** `GET /costs` を settle 先の origin から読む。token は `POST /settle` と `GET /costs` にだけ付ける（settle 設計 R3 の拡張）。redirect は拒否、本文は 256 KiB まで、1 回 3 秒まで【案】、再試行なし。
  注文のたびには呼ばず、短時間（案：60 秒）使い回す。同時の呼び出しは 1 つにまとめる。失敗した時に前の値を使ってよいのは、読んだ時刻から 10 分まで【案】。429 のあとは待つ。
- **R4（検査）** 応答は信用しない。200 の object で、chain id と token が route と一致し、使う値が 10 進の非負の整数の文字列で 30 桁まで、`overheadRate` が 0 以上 0.5 未満の数、`successfulItems` が 1 以上、`p90` が null でなく、`baseFeePerGas` と `asOfBlock` が null でないこと。
  違えば使えない。item の数は 500 まで読み、`l1Fee` が null の item は最大の計算から除く。
- **R5（売らない条件）** 次のどれかで、**注文を作る前に**新しい offer を断る（quote は固定の code・理由、標準入口は 503）：費用を読めない、ETH の価格が使えない（§3.1）、`settle > maxSettle`、`amount > maxAmount`、その日の件数が `maxPerDay`、`offerCap`、計算のあふれ。
  断るのは新しい offer だけで、発行済みの支払い・結果の読み取り・complete は続く。
- **R6（固定）** 額は注文の作成の時に 1 回だけ決め、以後変えない。同じ `requestId` の再取得は、記録の額を返す。見積もりの有効期間は今の offer の期限（quote 120 秒、標準入口は注文の期限）のまま。
  settle・上流への支払いの時に計算し直さない（実費が上がっても、発行済みの額で受ける）。
- **R7（件数）** 1 日の件数は、その route の記録のうち、**枠を予約した時刻**（記録に残す）の UTC の日が今日のもので、今の `offerCap` の数え方（`countsTowardOfferCap(intent, now) || activePurchases.has(quoteId)`）に入るものの数と、今日予約した発行の途中の数の和。
  数から外れるのは、Router がもう settle を始めないもの（払われ得ないことの保証ではない）。結果の分からない購入は残る。予約の時刻が読めない・承認の期限と合わない記録は、どの日の数にも入れる。
  quote と標準入口で共有し、注文を作る前に、await を挟まない 1 区間で数えて予約する。発行の途中で日が変わっても、予約した日の 1 件のまま（新しい日の枠は使わない）。
  journal から数えるので再起動で戻らない。`offerCap` の総数は日をまたいで残る。`maxSettle` は見積もりの上限で実費の上限ではない。件数の上限 × `maxSettle` を損失の保証とは言わない。
- **R8（承認と指紋）** quote の `subject` と記録に、額と内訳（上流、settle、withdraw、take、0.35% 分 `share`、端数、合計、費用を読んだ時刻）を残す。
  route の指紋には、式の種類と設定値（`factorBps`・`take`・`K`・`n`・`tip`・`l1Floor`・`maxSettle`・`maxAmount`。`maxPerDay` と `offerCap` は入れない）を入れ、計算した額と `ethPrice` は入れない。設定値が変わったら、変更前の quote では払えない（今と同じ扱い）。
  offer の照合は、設定の固定値ではなく、その注文のために計算した額と行う。復元した記録は、内訳の合計と offer の額が一致しなければ支払いに使わない。
- **R9（標準入口）** 402 の額は式で決めた額。買い手の credential の照合は、今と同じく発行した offer と行う。
- **R10（予算）** 予約は、その注文の額で行う。区分の 1 件の上限は `maxAmount` 以上であること（R2）。
- **R11（一覧・開示）** D-2 のとおり。README・MCP の説明と、公開の案内（llms.txt。この repo の外なので文案を設計 §8 に置き、有効化の時に足す）に、額が注文ごとに変わること、上限、断られることがあることを書く。費用の記録（wei、tx hash、ほかの呼び出し側の分）は、買い手に出さない。
- **R12（秘密）** token を log・ledger・journal・note・診断・例外・一覧に出さない。`/costs` の生の本文を残さない。
- **R13（hosted）** 既定は無効で、子の env と生成される設定が今と byte 一致。ETH の価格と時刻は host の env で変えられる（image を作り直さない）。値が無い・期限切れでも起動し、zUSDC の新しい offer だけ断る。
- **R14（既存の client）** `npm run sign` と標準の x402 client が、額の変わる offer をそのまま払えること（額の上限は 20,000 のまま）。`@subetha/payer` は zUSDC の route を扱わない（今と同じ）：一覧を読んで壊れないことだけを求める。

## 6. 受け入れ

- **AC-1** 式の計算：§3 の例と同じ値（settle 4,230、amount 17,040、share 60、`n` = 40 で 15,234。`overheadPpm` = 0 として）、`overheadPpm` の +1、境界、切り上げの向き、あふれ。`amount − share ≥ C` が範囲の中で成り立つ（性質の試験）。
- **AC-2** R4 の各違反、成功 0 件、全件未完成、率が null・0.5 以上、古い値（10 分の前後）、429、timeout、本文の超過、redirect、別の chain・token：どれも断る（10 分以内の前の値が使える場合を除く）。
- **AC-3** R5 の各条件で、SubEtha への注文の作成が 0 回。発行済みの支払いは完了する。
- **AC-4** 同じ `requestId` の再取得・再起動のあとも同じ額。計算のあとに費用や ETH の価格が変わっても、発行済みの額は変わらない。
- **AC-5** 100 件の同時の quote で、`/costs` の呼び出しが 1 回。60 秒の中の 2 回目の quote では 0 回、過ぎたら 1 回。
- **AC-6** 件数：両方の入口の同時の発行で `maxPerDay` を越えない、再起動で戻らない、未払いで期限切れの分は戻る、結果の分からない購入は戻らない、期限前に settle を始めず失敗した分は戻る、承認の期限をまたいで処理中の購入は残る、発行が日をまたぐ場合（予約した日に数える。記録の書き込みが翌日になっても同じ）、予約の時刻を書き換えた記録はどの日にも数える、`offerCap` は日をまたいで残る、見積もりが `maxSettle` とちょうど同じでも数える。
- **AC-7** 設定値の変更で指紋が変わり、`ethPrice` だけの変更では変わらない。固定の route の指紋と journal の行は変更前と byte 一致（golden）。
- **AC-8** 記録の内訳・額・offer のどれか 1 つを書き換えた復元は、支払いに使えない。
- **AC-9** 標準の x402 client（`@x402/fetch`）と quote の入口で、式の額で delivered。`npm run sign` が通る。20,000 を越える計算は 402 を出さずに断る。
- **AC-10** token の canary が、R12 の場所に出ない。`/costs` の token は settle 先の origin にだけ届く。
- **AC-11** hosted：無効なら byte 一致。有効で ETH の価格が無い・期限切れなら、ほかの route は売れ、zUSDC だけ断る。
- **AC-12** R2 の起動の検査の各条件と、§3.1 の範囲の両端・外。固定文に値が出ない。ETH の価格は、§3.1 の 6 つの場合のどれでも起動し、offer だけ断る（5 分以内の未来は使える）。
- **AC-13** 一覧（D-2）・MCP の説明が、式の route の額の上限を示す。`@subetha/payer` の route の読み取りが、式の route の入った一覧で壊れない。予約の額が注文ごとの額と一致する（違う額の 2 件で確かめる）。費用の記録（wei、tx hash）が買い手の応答に出ない。
- 緑の試験は、守っている code を壊して落ちることを確かめる。全体の試験は macOS と Linux。
