# SubEtha Router 要件定義 v1

対象リポジトリ: 本 worktree（`subetha/tokyo-20260925`）。本書は要件フェーズの成果物であり、設計・実装は含まない。

## 1. 目的

AI エージェントが「支払える方法」と API プロバイダが「要求する方法」が食い違う状況で、Router が
**受信レグ（inbound rail）で支払いを受け、送信レグ（outbound rail）で上流へ支払い直し、取得データを返す**。
最初の到達目標は SubEtha 受信 → Router → x402 Provider A の 1 経路を、ローカルで再現可能に動かすこと。

本 Router は次のいずれでもない: アトミックスワップ、FX/レート変換、ブリッジ、流動性提供、取引実行。
2 レグは**各レール個別に事前資金供給（prefunded）された独立支払い**であり、資産の交換ではない。

## 2. 所有権（再実装しない）

| 対象 | 所有 | 本リポジトリの扱い |
|---|---|---|
| 既存 chat（`chat-demo-v1-20260910`） | 別オーナー/別セッション | 会話・承認 UI・表示・履歴はそちらが所有。実インタフェースは設計時に実物を調査。native/proof 実行ホールドは尊重し再試行しない |
| Provider A/B（`market-data-providers-20260925`） | 別プロジェクト | 読み取り専用参照。編集・設定・鍵操作をしない。既存 A/B の allowance は Router の allowance ではない |
| 旧 PoC（`subetha-payment-router`） | 凍結された技術検証 | 契約・語彙の参照元。流用時は出典とライセンスを記録。過去の E2E 報告は**歴史的記録であり本提出物の合格証拠ではない** |
| Router 本体 | 本リポジトリ | orchestrator、rail adapter、journal、CLI/TCP 入口、設定・allowlist |

新規 UI と新規 Provider は作らない。`@zerc20/sdk` 等の公式/BUSL ソースは vendoring しない。

| # | 経路 | 優先 | 状態要件 |
|---|---|---|---|
| P1 | SubEtha 受信 → x402 Provider A | 最優先 | 本 v1 のスコープ |

P3–P5 は adapter 差し替えで到達できる設計であることを要件とするが、本 v1 では未検証扱いとする。

## 4. 機能要件

### 4.1 入口と経路
- FR-01 Router は上流 A/B の canonical ルート `GET /v1/eth/snapshot` のみを中継する。**クエリ文字列を付けない**、
  GET 以外を送らない、canonical host をそのまま用いる（A: `127.0.0.1:8402` / B: `127.0.0.1:8412` 既定）。
- FR-02 上流は設定の allowlist に列挙された `upstreamId` のみ解決可能。任意 URL プロキシを提供しない。
- FR-03 Router 自身の受信入口は 402 チャレンジ → 支払い提示 → データ返却の 1 リソースに限る。

### 4.2 オファーと束縛
- FR-04 受信側は自ら発行した offer だけを受理する。支払いヘッダの accepted offer は、nonce 既知・未失効・
  要求ルートに束縛・発行時 offer と拡張フィールド含め完全一致を、**intent/journal 作成前に**検証する（strict preflight）。
  preflight 不在の rail adapter では有料ライフサイクルを開始しない（fail closed）。
- FR-05 request / offer / 承認は同一 idempotency key の下で結び付ける。金額・受取先・ネットワーク・リソース URL の
  いずれかが不一致なら支払いを開始しない。承認は特定の offer と経路に束縛され、
  **未承認・拒否・承認後に対象 offer／経路／金額が変化した場合は、いずれのレグの支払いも開始しない**（再提示と再承認が必要）。
- FR-06 上流 offer の取得（quote）は支払いを伴わない純粋な読み取りの **discovery** であり、支払い証拠の検証ではない。
  quote は送信レグ実行前に必ず先行するが、それ自体は受信レグの正当性を何も保証しない。
- FR-06b 受信レグの資格情報・支払い証拠は、当該レールの**実契約に従って検証**する。これは FR-04 の
  offer 同一性検査（自らが発行した offer か）とは別の検査であり、両方が成功するまで settle を実行しない
  （verify-before-settle）。検証方式は実ランタイム契約（§8 U-01/U-02）に従い、推測で定義しない。

### 4.3 資産単位・金額
- FR-07 受信レグと送信レグの資産・小数桁・ネットワークを**別フィールド**で保持する。
  A: Base Sepolia `eip155:84532` USDC（6 桁, 既定 wire `10000` = $0.01）。
  B: Tempo Moderato `42431` pathUSD（6 桁, 既定 wire `10000`）。受信レグ資産は SubEtha V1 の実設定に従う（§8 U-01）。
- FR-08 生の数値を 2 レグ間でコピーしない。送信額は上流 offer の金額を権威とし、受信額は自身の見積りを権威とする。
  両者は独立で、レート変換をしない。
- FR-09 1 リクエストあたり上限と、プロセス寿命をまたぐ累積支出上限（件数と金額）を設定で強制する。
  上限超過は支払い前に拒否する。

### 4.4 決済ライフサイクルと耐久性
- FR-10 送信レグは `(paymentId, attempt)` 単位で **at-most-once**。試行は write-ahead で journal に記録してから実行する。
- FR-11 送信失敗は `not_sent` / `rejected` / `unknown` に分類する。例外・タイムアウトは必ず `unknown`。
  `unknown` に対する自動再試行・自動再支払いはしない。
- FR-12 B の `502 paid_data_unavailable`（課金成立・データ未提供、レシート付き）は
  「支払い済み・データなし」の終了状態として記録する。**自動返金・自動再購入・自動リトライをしない**。
- FR-13 journal は追記専用ファイルとし、再起動時に replay して状態を再構築する。
  再起動後も各 payment の status（`awaiting_payment` / `paid` / `delivered` / `paid_data_unavailable` / `unknown`）を
  同一値で読み出せる。復旧オペレーション、返金処理、再照合ワーカーは v1 では作らない（§6 DEFER）。
- FR-14 受信レグ settle の冪等性を**前提にしない**。同一 evidence での再呼び出しが安全か、どの条件下で安全かを
  実レール契約（§8 U-01）で確認し、確認できた範囲でのみ再呼び出しを許可する。安全性が確認できない再呼び出しは禁止する。
- FR-14b 受信レグの結果が不明な場合も、送信レグと同様に durable な `unknown` を保持し、
  自動再 settle をしない。`unknown` は人の判断による解決対象として記録に残す。

### 4.5 観測性
- FR-15 各 payment について、経路（inbound rail / outbound rail / upstreamId）、両レグの金額と資産、
  offer 指紋、試行回数、終了状態、証跡（burnTxHash / settleTx / payment-response ヘッダ等）を読み出せる。
- FR-16 秘密・鍵・生ログを成果物および状態ファイルに残さない。

## 5. 観測可能な受け入れ条件（ゲートは分離する）

段階ごとに独立したゲートとし、後段の合格を前段から推定しない。

- AC-1（無課金・ユニット）Router のオファー検証・単位保持・上限・journal replay を単体テストで確認できる。
- AC-2（無課金・TCP）実プロセスとして Router を起動し、別プロセスのクライアントから
  402 チャレンジ、不正/別レール資格情報の拒否、allowlist 外の拒否、クエリ付き・非 GET の拒否を確認できる。
  上流は setup-disabled もしくはローカルスタブでよく、署名・送金を行わない。
- AC-3（最初の実行可能 Router）**CLI もしくは TCP 経由**で 1 リクエストが
  「受信 402 → 受理 → 上流 quote → 送信レグ → データ返却 or 明示的終了状態」を通過する。
  この時点で chat 連携は不要であり、chat デモの合否とは別物である。
  支払いポート（受信/送信 rail）をスタブ・代替実装で注入する場合は、その実行を **synthetic（合成・無課金）** と
  明示的にラベル付けし、実決済ゲート（AC-4/AC-5）の証拠として扱わない。
- AC-4（受信レグ実決済）SubEtha 受信レグが実ランタイムで settle し、証跡を journal に記録できる。
- AC-5（送信レグ実決済）A へのテストネット支払いが成立し、canonical ルートのデータを取得できる。
- AC-6（B 経路・正常系）同一受信口から B へ 1 回の課金を行い、**Uniswap v3 参照価格の実データを取得して
  クライアントが受領**し、証跡が journal に記録される。これが B デモの合格条件である。
- AC-6b（B 経路・課金後失敗処理）課金成立後にデータ取得が失敗した場合（`502 paid_data_unavailable`）、
  レシート付きで「支払い済み・データなし」を終了状態として記録し、自動返金・自動再購入・自動リトライを行わない。
  AC-6 とは独立した条件であり、AC-6b のみの達成は AC-6 の合格ではない。
- AC-7（chat デモ）chat 上で、価格と対象 offer／経路の提示 → ユーザーの明示的承認 → **その承認に束縛された支払い**
  → 結果の受領 → 保存 → 再オープン後の同一 payment status と結果の表示、という因果が一続きに確認できる。
  未承認・拒否・承認対象の変更時に支払いが開始されないことも確認する。UI 実装は既存 chat の所有範囲であり、
  本要件は Router 側が満たすべき束縛と状態提供を対象とする。AC-3 とは別ゲートであり、AC-3 の合格は AC-7 を含意しない。
- AC-8（再起動安全性）AC-3 以降の状態で Router を停止・再起動し、既存 payment の status が変化しないことを確認できる。
- AC-9（再現性）README 記載の手順のみで、クリーンな環境から AC-1 / AC-2 / AC-3 を再実行できる。

AC-4 以降は実支払いを含むため、別途の支払い権限（§6）が必要。AC-1〜AC-3 は無課金で独立に達成する。

## 6. BLOCK（進行不可）と DEFER（意図的後回し）

BLOCK — 権限または実入力が揃うまで着手しない:
- B-01 実チェーン決済・実 settlement 全般（AC-4 以降）。受取先確定、資金供給元、署名・ブロードキャスト・faucet の
  明示的許可、支出上限の設定が個別に必要。ローカルのダミー 402 は支払い可能性の証拠ではない。
- B-02 SubEtha V1 の**実ランタイム詳細**（facilitator エンドポイント、受信資産、offer スキーマ、settle 契約）。
  これは設計フェーズの前提入力であり、現行デプロイを推測で記述してはならない（§8）。
- B-03 chat 実インタフェースへの接続。実物調査が前提で、chat 側の実行ホールドは本リポジトリで再試行しない。
- B-04 GitHub リモート作成・push・公開・デプロイ。ローカルコミット権限からは導けない。
- B-05 A/B Provider の「課金可能」前提での統合。A/B README の paid-status 節は stale で、保存済みの新しい運用状態が優先する。
  **fresh な paid readiness は主張しない。consumer 側（Router からの）統合は未検証と明記する。**

同一チェーン内 SubEtha 決済に LayerZero 等のクロスチェーン前提は**要求しない**（B-02 の未確定とは別問題）。
無課金の製品作業（AC-1〜AC-3）は chat 側のホールドや B-01 の解除を待つ必要がない。

DEFER — v1 では作らない:
- D-01 自動照合/reconcile ワーカー、自動返金、自動再購入、`unknown` の自動解決。
- D-02 **外部 Provider B 側**の replay ストア改善（mppx のストアはプロセス内メモリのみという既知制約）は延期する。
  これは Router の責務の延期ではない: Router は FR-10〜13 のとおり、**再起動をまたいでも同じ支払いの再送を抑止**し、
  実行済みか不明な試行を durable に保持しなければならない。`attempt` を繰り上げて新しい試行にすることで
  この抑止を回避してはならない（新しい試行は FR-11 の分類と支出上限の下で明示的に許可された場合のみ）。
  汎用的な復旧基盤は不要。
- D-03 P3/P4/P5 の実装と同一レールマトリクス。
- D-04 汎用マルチ Provider 選択、料金最適化、キャッシュ、複数リソース対応。
- D-05 認証・課金ダッシュボード、メトリクス基盤、finality 判定（mined/canonical までを扱う）。

## 7. 提出物としての要件

- S-01 セットアップは Node バージョン・インストール・起動・検証コマンドを含め再現可能に文書化する。
- S-02 境界（自己ホスト Provider であること、testnet 専用、mainnet データ読み取り、参考値であり約定可能でないこと、
  Router が交換/ブリッジでないこと）を README と本書で明示する。
- S-03 レビュー済み・検証済みの小さなマイルストーンごとにローカルコミットする。空コミット・過去改変・秘密混入をしない。
- S-04 流用コードは出典・ライセンス・改変点を記録する。公式 `@zerc20/sdk` / BUSL ソースは含めない。

## 8. 未確定の設計・ランタイム入力（設計フェーズの前提）

| ID | 必要な入力 | なぜ必要か |
|---|---|---|
| U-01 | SubEtha V1 受信レールの実 facilitator base URL、資産・小数桁・チェーン、offer/accepted スキーマ、settle レスポンス形 | FR-04/07/14 と受信 adapter を確定できない |
